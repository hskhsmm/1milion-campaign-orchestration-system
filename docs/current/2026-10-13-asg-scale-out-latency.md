### 3.5 드레인 속도 차이 → 원인: Redis 노드 CPU 크레딧 고갈 + Bridge 직렬 RPOP

| | 재고 소진 시 llen | 드레인 시간 | 평균 속도 |
|---|---|---|---|
| 1차 | 1,385,385 | 18분 33초 (11:06:14 → 11:24:47) | 약 1,250/s |
| 2차 | 1,143,409 | 4분 45초 (11:39:41 → 11:44:26) | 약 4,000/s |

두 경우 모두 드레인 구간은 앱 3대였고, 1차 드레인 중 앱 CPU는 21~25%로 낮았다.

#### 3.5.1 병목은 Bridge(Redis → Kafka)였다 [확정]

- 1차: `successCount + llen ≈ 1,500,000` (11:09:28 기준 325,191 + 약 1,160,000). Kafka에 쌓인 양이 거의 없음 → Kafka·DB는 Bridge가 넘겨주는 만큼 바로 처리했다.
- 2차: 같은 합이 약 133~144만 → Kafka에 최대 약 17만 건 적체. Bridge가 DB보다 빨랐다(DB 반영 약 4,200/s).
- Bridge는 메시지마다 `RPOP` 1회(+ 비동기 Kafka send)를 **직렬로** 반복한다(`ParticipationBridge.drainCampaignQueue`). 인스턴스당 처리량 ≈ 1 / RPOP 왕복 시간이다.

Bridge 발행량 (`bridge_messages_published_total`, 인스턴스별 /s):

| | 2a 인스턴스 | 2b 인스턴스 | 합계 |
|---|---|---|---|
| 1차 드레인 | 520~690 | 400~500 | 약 1,300~1,900 (11:16~11:18 약 300으로 정체) |
| 2차 드레인 | 1,500~1,800 | 1,100~1,150 | 약 4,500 |

#### 3.5.2 두 캠페인 큐는 다른 Redis 노드에 있었다 [확정]

큐 키 `queue:campaign:{id}`는 hash tag `{id}`로 샤드가 정해진다.

| | 샤드 (primary) | AZ | 노드 CPU | CPUCreditBalance | RPOP 평균 지연 |
|---|---|---|---|---|---|
| 1차 (70) | 0002-001 `172.31.46.169` | **2c** | **10.0% 평탄** (11:07~11:23) | **0.0005** (11:09~11:19) | **1.4~2.1ms**, 정체 구간 7~10ms |
| 2차 (71) | 0003-001 `172.31.3.194` | 2a | 15~20% | 2.7~4.0 | **0.45~0.63ms** |

- 노드 타입은 `cache.t3.micro`(버스터블, 기준 성능 10%). Redis는 env-up마다 새로 만들어져(이번 10:48:55 생성) **크레딧 약 1.4로 시작**한다.
- 1차: 부하 중 0002-001 CPU 23%로 크레딧 소진(11:05 0.17 → 11:09 0.0005) → 드레인 내내 CPU가 **정확히 10%로 묶임**. 이 시기 RPOP 지연이 3~4배. [확정: CloudWatch, Prometheus `lettuce_seconds`]
- 2차: 0003-001은 1차 동안 쉬면서 크레딧이 쌓여(4.4) 소진되지 않았다.
- AZ 영향: 앱은 2a·2b에만 있다. 1차 노드(2c)는 모든 인스턴스에서 AZ를 건넜고, 2차 노드(2a)는 2a 인스턴스와 같은 AZ였다. 2차에서 2a 인스턴스가 2b보다 약 1.5배 빨랐다. [확정]
- 11:15~11:17 정체(RPOP 7~10ms)는 크레딧 고갈 상태에서 Engine CPU가 오히려 2.5%로 떨어진 구간이다. 다른 작업이 묶인 CPU를 쓴 것으로 보이나 원인은 확인하지 않았다. [미확정]
- 처음 의심한 "신규 인스턴스 합류 시점(Kafka 리밸런스)"은 3.5.1에 따라 원인이 아니다(Kafka 적체가 없었다).

#### 3.5.3 부하 중 Bridge 기아 [확정]

부하 구간에 프로세스 CPU가 97% 근처인 인스턴스는 Bridge 발행이 **5~13/s**로 거의 멈췄고, 83% 근처인 인스턴스는 300~400/s였다(2차 11:35~11:37, 1차도 같은 양상). 부하 중 큐가 110~140만까지 쌓이는 주된 이유다. Tomcat 요청 스레드에 밀려 스케줄러 스레드가 CPU를 거의 못 받는 것으로 보인다. [메커니즘은 추정]

#### 3.5.4 의미

- 드레인 속도가 **캠페인 id가 어느 샤드에 걸리느냐**와 **그 노드의 크레딧 잔량**에 따라 3배 달라진다. 9/19·9/25 등 과거 결과 비교 시에도 이 변수를 통제하지 않았다.
- 개선 후보: (1) Bridge `RPOP key count`(Valkey 7.2 지원)로 왕복 1회에 여러 건 → 지연 영향 제거, (2) Redis 노드를 버스터블이 아닌 타입으로, (3) Redis primary AZ를 앱 AZ(2a·2b)와 맞춤, (4) 부하 중 Bridge 기아 완화.

## 4. 결론

- 증설 경로(알람 → 기동 → CodeDeploy → healthy)는 2회 모두 실패 없이 동작했다. [확정]
- 감지 시간: 약 9분(9/25) → 5분 47초(1분 지표) → **3분 31초(Step)**. [확정]
- 투입까지 7분 35초 → **5분 9초**. 8분짜리 순간 폭주 테스트에서 증설 인스턴스가 약 2분 반 동안 기여했다.
- 남은 한계: 감지(약 3분 반)는 CloudWatch 1분 지표 발행 지연과 알람 평가 주기 때문에 더 줄이기 어렵다. 순간 폭주를 완전히 따라가려면 사전 증설(Scheduled Scaling)이 필요하고, 증설 효과 자체를 보려면 20~30분 지속 부하(capacity 모드) 테스트가 필요하다.
