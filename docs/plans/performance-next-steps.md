# 성능 개선 중간 정리와 다음 작업

> 갱신: 2026-11-04 / 현재 코드 확인 기준: main `6f3fa37`(PR #120~#122). 2026-11-04 결과와 다음 작업은 [5-1장](#5-1-2026-11-04-결과와-다음-작업).
> 목적: 확인한 사실, 아직 설명하지 못한 원인, 다음 실험, 하네스 자동화 범위를 한곳에서 확인한다.
> 이번 30만 건 비교는 개선 방향을 찾는 탐색이다. 150만·200만 최종 검증이나 운영 SLO 달성을 대신하지 않는다.

## 1. 지금 어디까지 왔나

전달 안정성과 실패 재처리의 기본 구조를 만든 뒤, 실제 병목을 나누어 측정하는 단계까지 왔다. 현재 큰 목표는 **접수한 이벤트의 정합성을 유지하면서 API 지연·Queue 적체·전체 완료 시간을 줄이고, 최종적으로 200만 건을 검증하는 것**이다.

```text
사용자 → ALB → 앱의 참여 API
                  ↓ Redis Lua: 재고 차감·중복 확인·Queue 적재
                202 반환
                  ↓
          앱의 Bridge: Queue → in-flight claim
                  ↓ Kafka 발행 성공 후 claim 제거
                Kafka
                  ↓
          앱의 Consumer → JDBC batch → DB
                  ↓ 영구 오류는 DLQ DB에 격리
          운영자가 DLQ Replay Job 실행·결과 대조
```

현재 API·Bridge·Consumer는 같은 앱 인스턴스에서 실행된다. Kafka의 비동기 전달 경계는 있지만 **실행 자원의 분리까지 된 것은 아니다.** 서로 다른 스레드여도 CPU·힙·GC 등은 공유한다.

in-flight는 최초 참여 접수 때 만드는 복제본이 아니다. 접수된 이벤트는 Queue에 남아 있고, **Bridge가 꺼내는 시점에 Lua로 Queue→in-flight 이동을 원자적으로 처리**한다. Kafka 성공 후 제거하고, 미확인 claim은 만료 복구한다. 202 전에 Kafka 저장이나 Redis replica 복제 완료를 기다리는 구조는 아니다.

## 3. 오늘 AWS에서 확인한 수치

동일 앱 코드·이미지, t3.small, shared-iterations 30만 건·500 VU 조건이다. 2대에서 3대로 늘린 뒤, 재배포 없이 같은 3대로 다시 시험했다.

- **증설은 적체와 완료 시간을 줄이는 데 도움이 됐다.** 다만 첫 3대 시험에서는 API 꼬리 지연이 악화됐다.
- **재배포 없이 다시 주니 API 지연이 크게 줄었다.** p99는 약 1.29초→0.52초였다. 앱 코드 최적화 효과가 아니라 실행 상태가 다른 시험의 결과다.
- **접수가 빨라져도 Queue는 커질 수 있다.** 재시험은 30만 요청이 약 95초 대신 약 62초에 몰렸다. 따라서 최대 Queue와 부하 종료 후 처리 시간이 늘었다.
- **이번 규모는 모두 처리했다.** 이것은 지속 유입을 계속 따라잡는다는 뜻이 아니다. 고정 RPS 시험과 혼동하지 않는다.

비교 한계: 각 조건 1회, 캠페인별 같은 Redis primary지만 다른 슬롯, 이전 참여 키 유지, JVM 실행 이력·시험 시각 차이가 있다. 표본 주기는 약 5~6초이며 구간별 Bridge 속도는 각 시험의 경계를 제외한 counter 차이다. 이를 고정 유입률에서의 보편적인 성능 개선율로 해석하지 않는다.

## 4. 현재 원인에 대해 어디까지 말할 수 있나

### 신규 앱 워밍업: 근거가 강해졌지만 단일 원인 확정은 아님

신규 앱의 JVM 누적 컴파일 시간 증가량은 첫 시험 약 106.7초, 재시험 약 44.0초였다. 재시험에서 기존 앱은 약 2.8/3.0초였다. 신규 앱 Young GC pause 누적 증가량도 약 2.58초→1.08초로 줄었다.

이는 JVM 워밍업·컴파일 및 CPU 경쟁이 영향을 줬다는 가설을 뒷받침한다. 컴파일 시간은 앱 전체가 멈춘 시간이 아니며, 표본 구간 길이도 다르다. 시간 동반 변화만으로 지연의 전부를 설명하지 않는다.

재시험에서도 서버별 1분 창 p99 추정 최댓값은 신규 약 759ms, 기존 약 149/174ms로 차이가 남았다. 이것은 k6 전체 p99와 다른 통계다.

**클래스 로딩과 JIT 컴파일은 다르다.** CDS/AppCDS는 검토 가능한 기동 최적화 후보지만, 이번에 클래스 로딩 지연을 따로 측정한 것은 아니다. 일반적인 CDS가 애플리케이션의 모든 JIT 최적화 결과를 대신 준비해 주는 것도 아니다. 따라서 클래스 로딩 최적화를 곧바로 이번 해결책으로 정하지 않는다.

### Bridge 순차 claim: 측정된 대기이며 batch화는 개선 가설

유입이 끝난 drain 구간에도 claim 평균 약 1.4~1.6ms가 건별로 발생했다. Kafka send 동기 호출보다 claim 쪽 대기 기여가 컸다. 이는 작은 batch claim을 비교할 근거다.

다만 claim timer에는 네트워크·Lettuce·스레드 대기·직렬화 등이 포함될 수 있다. 이를 Redis Lua 자체가 1.5ms 실행됐다고 말하거나, Redis 서버만 병목이라고 단정하지 않는다.

### API·워커 자원 경쟁: 유력하지만 분리 실험은 아직

유입 중과 유입 종료 후 Bridge 처리량·CPU가 크게 달라지고, 역할이 같은 JVM에 묶여 있다. 자원 경쟁의 강한 정황은 있다. 하지만 **같은 총 CPU·메모리로 역할을 분리한 A/B**를 하지 않았으므로 해결 효과의 크기는 아직 모른다.

역할 분리에서 함께 정할 것:

- 역할 선택 방식(예: 설정값 하나로 API / worker / 공용). 스케줄러(Bridge drain·reclaim), Kafka listener, 관리 Job이 어느 역할에서 켜지는지.
- ALB 대상은 API 역할만. worker의 배포·health check·스케일 기준(Queue·lag), 최소 대수.
- worker 정상 종료 순서: claim 중지 → Kafka producer flush → 대기 ACK 비우기(시간 상한) → Redis·DB 연결 종료. Docker·CodeDeploy 종료 대기 시간과 맞춘다.
- 역압·ACK 대기열 단위(캠페인 또는 샤드)를 worker 설계에서 정한다.
- 비교는 같은 총 자원 A/B와 서버를 추가한 비교를 구분하고, 한 번에 한 변수만 바꾼다.

### batch claim에서 지켜야 할 경계

- 한 Lua가 너무 많은 이벤트를 오래 처리하지 않도록 작은 크기부터 비교한다. 크기는 측정으로 정한다.
- Queue→in-flight 원자성, 이벤트별 고유 claim, in-flight 상한, 만료 복구·늦은 ACK 보호를 유지한다.
- 동일 campaign 해시 태그를 유지한다. 여러 샤드에 걸친 키를 한 Lua에 넣지 않는다.
- Kafka 실패·앱 종료·ACK 실패 시 원본 보관과 재처리를 다시 확인한다. 성능을 위해 기존 유실 창을 되살리지 않는다.
- batch 크기 외 주기·스레드 수·in-flight 상한 등을 동시에 바꾸지 않는다.

### 역할 분리는 우선 배포 역할부터

처음부터 별도 저장소·마이크로서비스로 전면 분리할 필요는 없다. 같은 코드·이미지에서 API 역할과 Bridge/Consumer 역할을 선택해서 실행하는 방식부터 설계한다. Bridge와 Consumer까지 별도로 나눌지는 관측 결과로 결정한다.

스케줄러·Kafka listener·관리 Job이 어느 역할에서 켜지는지, worker 배포·정상 종료·상태 확인·복구 방법도 함께 정해야 한다. 스레드 풀만 나누면 CPU·힙·GC 경쟁은 남는다.

같은 총 자원 비교와 서버를 추가한 비교를 구분한다. 분리 후 API 용량이 너무 작아지는 경우나 Redis·RDS가 새 병목이 되는 경우도 확인한다.

### Queue 상한은 처리 속도와 다른 문제

Queue는 접수 속도가 드레인보다 빠른 동안 쌓인다. 중요한 것은 순간 증가 자체보다 **최대 잔량·메모리 여유·최종 드레인 시간·접수 정책**이다.

앱의 건수 상한은 이벤트 크기·다른 키·in-flight를 포함한 실제 메모리 안전성을 보장하지 않는다. 상한만 높여 해결하지 않는다. 드레인을 개선하고 메모리·거절 정책을 측정한 뒤 조정한다. in-flight 10,000 상한은 캠페인 전체 150만/200만 수용량이 아니라 Bridge가 동시에 선점하는 양의 제한이다.

## 6. 하네스·API 덕분에 평가와 자동화가 쉬워졌나

**그렇다. 다만 현재는 도구와 계약이 갖춰진 부분 자동화 단계다.** AI가 문서를 읽는 것에 더해, 실행·관측·결과 대조의 경로가 만들어졌다. 모든 것을 한 명령으로 안전하게 실행·판정하는 제품이 완성된 상태는 아니다.

| 층 | 현재 재사용할 수 있는 것 | 남은 연결 |
| --- | --- | --- |
| 작업 계약 | AGENTS.md, 문서 목차, 비교 조건과 PASS/FAIL/INCONCLUSIVE 절차 | 코드 변경과 함께 최신 상태 유지 |
| 실행 | 기존 run-test.sh의 integrity/capacity, 동적 ALB 주소 확인, k6 요약 JSON 저장 | 실행 ID 아래 사전 점검·수집·종료를 묶는 최소 진입점 |
| 관측 | Prometheus·Grafana·Bridge 구간 계측, Redis 감시, MCP 지표 조회·알림 코드 | 실행별 시간 범위 고정·누락 확인·원본 자동 보관 |
| 업무 API | 캠페인 상태, DLQ 조회·실행·재개·DB 결과 대조 | bounded polling과 결과 저장을 기존 테스트에 연결 |
| 최종 판정 | 가이드에 증거·판정 기준 정의, SQL로 최종 건수·중복 확인 | 전체 실행을 묶는 판정기 통합과 회귀 시험 |

현재 확인한 코드에는 `stress-test/harness/`가 없다. 이번 AWS 실행에서 사용한 수집·메모리 가드·drain 대기·비교 계산 일부는 원격 `/tmp`와 로컬 임시 스크립트다. 동작한 실험 도구이지만 저장소의 공통 하네스로 통합됐다고 말하지 않는다. 원격 별도 하네스 브랜치의 최신 구현을 이 문서 작업에서 새로 검토한 것은 아니다.

### 실제로 호출할 수 있는 API

| 목적 | 메서드·경로 | 자동화에서의 활용·주의 |
| --- | --- | --- |
| 캠페인 생성 | POST /api/admin/campaigns | 실행별 새 캠페인 생성. 환경을 변경하는 동작 |
| 캠페인 목록 | GET /api/admin/campaigns | 대상 확인 |
| 참여 결과·재고 조회 | GET /api/campaigns/{id}/status | 성공·실패 건수와 재고 polling. Queue/in-flight·중복 검증까지 대신하지 않음 |
| DLQ 검색 | GET /api/admin/dlq-replay/messages | 캠페인·상태·사유별 격리 결과 조회 |
| Replay Job 시작 | POST /api/admin/dlq-replay | dry-run/필터/maxItems를 지정해 실행. 실행 ID 보관 |
| Replay 실행 결과 | GET /api/admin/dlq-replay/executions/{executionId} | 업무 실행 상태·항목 결과 조회 |
| Replay 재개 | POST /api/admin/dlq-replay/executions/{executionId}/resume | 같은 업무 실행의 커서 재사용. confirmStopped는 운영자 확인이지 분산 락이 아님 |
| Replay DB 대조 | GET /api/admin/dlq-replay/executions/{executionId}/verification | 원래 campaign/user/sequence의 SUCCESS DB 행을 대조. afterId/size로 항목 페이지 조회 |
| 정합성 복구 | POST /api/admin/consistency-recovery, GET /executions/{executionId} | 검사·조건부 수정과 업무 실행 결과. 실행과 조회의 권한·영향을 구분 |
| 일반 Batch 상태·이력 | GET /api/admin/batch/status/{jobExecutionId}, GET /api/admin/batch/history | 현재 Batch 저장소의 한계와 실행 앱을 고려해 사용 |

특히 `verification`은 **Kafka 재발행 성공과 DB 복구 성공을 구분할 수 있게 한 부분**이다. 상태 API만 보고 끝내던 것보다 자동 평가를 구체화하기 쉬워졌다.

단, Batch 기술 메타데이터는 현재 확인된 Resourceless/in-memory 구성의 한계가 남아 있다. BATCH 테이블이 있다는 이유로 JDBC JobRepository가 활성화됐다고 말하지 않는다. 업무 실행 테이블의 `replayExecutionId`와 기술적인 `jobExecutionId`를 구분하고, 재시작·다중 앱을 넘는 장기 실행 추적은 업무 실행 ID를 중심으로 한다.

Prometheus HTTP API로 지표를 구간 조회할 수 있고 MCP도 조회·보고 도구를 제공한다. 하지만 **MCP 보고서는 캠페인별 최종 SQL 정합성 판정기의 대체물이 아니다.** 일부 MCP 도구는 검사·알림 상태를 변경하므로 읽기 전용 조회와 구분한다. Slack 코드 존재와 실환경 발송·복구 검증 완료도 구분한다.

### 다음에 붙일 자동화는 작게

이번에 반복한 절차를 기존 테스트에 연결한다.

```text
실행 ID와 조건 저장
 → 배포·용량·기존 작업·메모리 사전 점검
 → 승인된 테스트 실행 + 같은 시간축의 지표 수집
 → 제한 시간 안에서 Queue/in-flight/lag 수렴 대기
 → 상태 API + 최종 SQL + 필요 시 Replay verification 대조
 → 원본 경로·비교값·누락 증거 기록
 → 최종 검증이면 사전 합의한 기준으로 판정
```

- API 시작 응답은 Job 완료가 아니다. 성공 응답을 받으면 실행 ID로 상태를 조회한다.
- polling에는 timeout·실패 종료·명시적 결과를 둔다. 응답 없음·빈 메트릭을 성공으로 해석하지 않는다.
- 캠페인 Queue gauge가 여러 앱에 중복 노출되면 합산하지 않는다. 조회 목적에 맞는 max 집계를 쓰고 최종 잔량은 실제 LLEN/ZCARD로 확인한다.
- 부하 발생기의 202, Bridge 발행, Consumer 성공 경로, 물리 DB 신규 행 수를 구분한다.
- 탐색에 운영 SLO나 메모리 안전 임계치를 임의로 만들어 붙이지 않는다. 최종 판정에서 필수 증거가 없으면 INCONCLUSIVE로 남긴다.
- 하네스 연결을 위해 지금 별도 대형 프레임워크나 대량 문서 생성기를 만들 필요는 없다.

## 7. 이후로 미루는 것과 남은 위험

- Redis primary 장애 직후 아직 복제되지 않은 202 접수 데이터 유실: in-flight만으로 해결되지 않음.
- 한 캠페인의 동일 해시 태그가 한 샤드에 몰리는 구조: 3샤드 총 메모리를 한 캠페인이 모두 쓰는 것은 아님. 샤드와 replica의 역할도 다름.
- 브로커 장애·리더 선출과 DB 정합성을 연결한 반복 가능한 증거, 남은 장애 조합: 별도 검증 과제.
- Batch JDBC 메타데이터·다중 실행 동시성·나머지 Job 운영성: 별도 범위.
- 전 구간 접수→DB 반영 p95/p99·oldest-event age: API p99나 Consumer 일부 timer로 대체하지 않음.
- Kafka 완전 재구축 코드화, 3샤드 병렬 캠페인 설계, Kubernetes 전환: 200만 검증 전의 필수 작업으로 확대하지 않음.
