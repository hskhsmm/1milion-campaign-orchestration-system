# API·워커 분리 A/B 시험 계획

같은 앱 서버 3대에서 역할을 분리하면 API의 꼬리 지연이 줄고, Redis 적체와 최종 DB 반영 시간도 허용 범위에 들어오는지 확인한다. 11월 4일 앱 2대 시험의 서버 측 p99 659ms와 Kafka 발행 완료 시간은 당시 관측값이다. 이번 시험은 공용 3대에서 k6 응답 시간과 최종 DB 반영 시간의 기준선을 새로 측정한다. [11월 4일 운영 비교](../reports/2026-11-04-ops-batch-claim-ack.md)

## 비교 구성

| 항목 | A 공용 | B 분리 |
| --- | --- | --- |
| 앱 EC2 | 공용 3대 | API 2대 + 워커 1대 |
| HTTP 참여 요청 | 공용 3대 | API 2대 |
| Bridge claim·reclaim, Kafka Consumer | 공용 3대 | 워커 1대 |
| 앱 사양·이미지 | `t3.small` 3대, 동일 이미지 digest | A와 동일 |
| claim 묶음 크기·ACK | `N=10`, 묶음 ACK | A와 동일 |
| Kafka·Redis·DB | Kafka `t3.small` 브로커 3대, 같은 Redis와 DB 구성 | A와 동일 |
| 부하 발생기·지표 수집 | `terraform-mcp` `t3.large` 1대에서 k6와 Prometheus | A와 동일 |

두 구성 모두 기동 후 역할, ALB 대상, 이미지 digest를 확인하고 같은 준비·워밍업 절차를 적용한다. 시험 중 앱은 총 3대로 고정한다. 시작 3대·최대 4대는 이후 배포 설정과 증설 시험에 반영한다. 4번째 인스턴스의 역할과 `N=25·50` 효과는 첫 A/B가 끝난 뒤 각각 비교한다. [앱 ASG](../../infra/asg.tf) · [Kafka·MCP EC2](../../infra/ec2.tf)

### 앱 실행 역할

같은 이미지에서 `CAMPAIGN_ROLE`로 역할을 선택한다. 설정을 생략하면 `combined`로 기동한다. 허용 값은 `combined`, `api`, `worker`이며, 잘못된 값은 기동 오류로 처리한다.

| 실행 경로 | combined | api | worker |
| --- | --- | --- | --- |
| 참여·캠페인·수동 배치 관리 HTTP | 켜짐 | 켜짐 | 꺼짐 |
| Bridge·Kafka Consumer | 켜짐 | 꺼짐 | 켜짐 |
| Redis Queue 지표 수집 | 켜짐 | 켜짐 | 켜짐 |
| 정기 집계·배치 메타데이터 정리 | 기본 켜짐 | 꺼짐 | 기본 꺼짐 |

워커의 Actuator는 헬스 체크와 지표 수집에 사용한다. API와 워커의 Actuator를 모두 Prometheus에서 수집하고, 같은 Redis Queue를 여러 앱이 읽으므로 `max by (campaignId) (redis_queue_size)`로 집계한다. 분리 구성에서는 워커 중단 중에도 API에서 Queue 지표가 갱신되는지 확인한다. 정기 배치는 `CAMPAIGN_SCHEDULED_BATCH_ENABLED=true`를 지정한 워커 한 대에서 실행할 수 있다. 분리 구성의 공용 워커 설정에 이 값을 켜면 워커마다 같은 정기 작업을 등록하므로, 필요하면 단일 실행 대상을 지정한다. A/B에서는 양쪽 모두 `CAMPAIGN_SCHEDULED_BATCH_ENABLED=false`로 맞춘다.

## 실행 순서

A는 `combined-fixed`, B는 `split-fixed`로 기동한다. 배포 선행 조건과 앱 그룹만 내렸다 올리는 방법은 [운영 가이드](../../ops/README.md#앱워커-레이아웃-전환)를 따른다.

1. 공용 3대로 짧게 탐색해 k6가 재현할 수 있는 유입률과 안정 구간을 찾는다. 목표 RPS, 안정 구간 길이, RPS 허용 오차, drain 관측 시한, Redis 메모리 중단 기준과 측정 주기를 실행 기록에 확정한다. 각 실행은 고유 캠페인과 합성 사용자 ID를 쓰고, 같은 Redis primary에 매핑되는 캠페인을 고른다. 실행 전 Queue·in-flight·lag가 0인지 확인하고 잔류 키와 시작 메모리를 기록한다.
2. **고정 유입률 시험**은 k6 arrival-rate 방식으로 같은 참여 요청률을 유지한다. 안정 구간의 실제 유입률, `dropped_iterations`, 참여 API p95·p99 및 오류율을 기록한다. 재고 소진이나 같은 사용자의 재요청이 성능 측정에 섞이지 않도록 재고와 입력을 준비한다.
3. **30만 건 총량 시험**은 `shared-iterations`, 500 VU, 참여 요청 300,000건으로 고정한다. 동일한 입력 건수에서 접수와 발행, 최종 DB 반영, 최대 적체를 대조한다. 역할별 CPU, 캠페인 Redis Queue·in-flight, primary별 메모리, Kafka lag, DB 반영률과 Hikari 대기를 기록한다.
4. 시험별로 구성당 유효 실행 3회를 목표로 한다. 먼저 공용 기준선의 편차를 확인하고 B 측정 전에 합격선을 확정한다. 이어지는 비교에서는 가능한 한 구성 순서를 번갈아 실행하고, 실행별 값과 구성별 중앙값을 남긴다. `terraform-mcp`의 CPU·크레딧·메모리와 Prometheus 수집 공백도 함께 확인한다.

## 개선 채택 기준

아래 수치는 공용 3대의 편차를 확인하기 전 제안값이다. B 결과를 열기 전에 기준과 변경 이유를 실행 기록에 남긴다.

| 항목 | 기준 |
| --- | --- |
| 고정 유입률에서 API 지연 | 동일한 목표·실제 유입률에서 실행별 k6 p99 중앙값은 A 대비 20% 이상 감소, p95 중앙값의 증가는 5% 이내 |
| 30만 건의 DB 반영 완료 | 첫 참여 요청부터 해당 캠페인의 마지막 성공 반영을 확인할 때까지의 실행별 시간 중앙값은 A 대비 증가 5% 이내 |
| 정상 시험 정합성 | 30만 요청의 202 = Kafka 성공 발행 = DB 성공 30만 건. 합성 사용자·순번 누락과 중복, 예상 밖 5xx·timeout, ACK 거부·실패, reclaim 및 DLQ 0건 |
| 적체와 자원 | 고정 유입률의 안정 구간에서 Queue·Kafka lag가 계속 불어나지 않고, 종료 후 합의한 시한 안에 Queue·in-flight·lag 모두 0. 실제 Redis 메모리와 eviction 징후를 확인하고, 사전에 정한 중단 기준을 적용 |

지연과 완료 시간은 구성별 중앙값으로 비교하고 정합성과 자원 기준은 각 유효 실행에서 확인한다. 고정 유입률 시험은 실제 유입률이 합의한 오차 이내이고 `dropped_iterations=0`일 때 유효하다. 부하 조건이 어긋나거나 증설·배포 변경·필수 증거 누락이 발생하면 그 비교는 `INCONCLUSIVE`로 기록한다. 정합성 위반을 직접 확인한 실행은 실패로 기록한다. 실험의 채택 기준과 최종 150만·200만 검증의 PASS/FAIL 판정은 [테스트 가이드](../../stress-test/TEST_GUIDE.md#83-최종-검증-판정)에 따라 구분한다.

## 실행 기록

- 실행 ID, Git SHA, 이미지 digest, 구성별 역할·인스턴스, 시작 시각, 워밍업 방식, 캠페인 ID와 Redis primary, 시험 파라미터를 남긴다.
- 첫 참여 요청·마지막 응답·Kafka 발행 완료·최종 DB 반영 확인의 시각을 따로 기록한다. 관측 주기와 집계 구간을 함께 저장한다.
- 실제 Redis 잔량은 `LLEN`·`ZCARD`를, 최종 성공·중복은 DB 조회를 사용한다. 캠페인별 Kafka 성공 발행과 ACK·reclaim 지표를 대조한다.
- 실행 ID 아래 k6 원본, Prometheus 쿼리와 결과, Redis·DB 대조, 유효성 및 채택 판정을 묶는다. 조회 실패나 지표 공백은 별도 상태로 기록한다.

역할 분리 구현과 3대 배포 구성, [로컬 워커 종료·복구 검증](../reports/2026-11-07-api-worker-local-recovery.md)을 마쳤다. AWS에서 역할·ALB·Consumer 파티션 할당과 소량 정합성을 확인한 뒤 이 시험을 진행한다. 30만 건에서 기준을 충족한 구성은 150만 재검증과 200만 총량 검증 후보로 삼는다.
