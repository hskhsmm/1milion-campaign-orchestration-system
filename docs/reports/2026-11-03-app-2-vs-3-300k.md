# 앱 2대와 3대의 30만 건 비교

> 2026-11-03, 앱·테스트 스크립트 5b110eb. t3.small, shared-iterations 30만 건·500 VU.
> 결과: 3대에서 남은 작업은 더 빨리 처리됐지만 API p95/p99는 나빠졌다. 단순히 서버 수를 늘리면 모든 지표가 좋아진다고 결론 내리지 않는다.

## 맞춘 조건과 다른 조건

- 앱 코드·이미지 digest·인스턴스 사양·부하 스크립트·요청 수·VU는 동일하다. batch claim 등 코드 최적화는 적용하지 않았다.
- ASG desired만 2→3으로 올렸다. min=2/max=3·자동 증설 정책·자동 축소 비활성 설정은 유지했다. 4대 설정으로 바꾸지 않았다.
- 새 인스턴스 i-02de8f885ebb154d0(2b)의 이미지 일치, health UP, ALB healthy, Prometheus up을 확인했다. 컨테이너 기동 후 최소 150초를 기다렸다. 이는 실제 업무 요청을 충분히 처리한 워밍업을 의미하지 않는다.
- 캠페인 107과 110은 같은 Redis master(172.31.36.51)를 사용한다. 서로 다른 슬롯이지만 같은 master인지 확인했다. ID를 맞추는 과정에서 108·109를 각각 재고 5로 만들어 전량 처리했고 활성 Set/잔량 0을 확인했다.
- 이전 데이터는 지우지 않았다. 따라서 3대 시험은 기존 30만 참여 키가 추가로 남은 상태다. 메모리 절댓값을 서버 수의 효과로 비교하면 안 된다.
- 기존 2대는 앞선 시험을 수행한 JVM이고 신규 1대는 첫 대규모 요청이다. 신규 노드의 캐시/JIT/연결 상태까지 동일하게 통제한 실험은 아니다. 각 조건 1회 관측이다.

두 시험의 부하/종료 시점은 약 5~6초 수집 주기로 관측했다. 정확한 drain 완료 시각을 보장하는 값은 아니다. Phase별 평균은 각 실행의 경계 구간을 제외한 counter 차이로 계산하므로 동일한 벽시계 구간이나 고정 arrival-rate 비교가 아니다.

3대에서 전체 확인 시간은 약 37%, 부하 종료 후 확인 시간은 약 48%, 최대 Queue는 약 25% 줄었다. drain 발행률은 약 64% 높았다. API 평균은 약 11% 줄었지만 p95는 약 20%, p99는 약 33% 늘었다. 한쪽만 골라 성능 향상을 주장하지 않는다.

## 왜 신규 인스턴스를 따로 봐야 하나

3대 시험 유입 구간의 CPU 평균은 기존 2대 약 63%·69%, 새 인스턴스 약 95%였다. 기존 2대는 앞선 시험의 약 96~98%에서 여유가 생겼다. 그러나 새 인스턴스의 초기 claim 평균은 해당 구간 약 62ms로 길었다.

실제 서버별 HTTP histogram도 따로 조회했다. 부하 시작 30초 이후~종료 감지 구간의 1분 창 p99 추정 최댓값은 기존 2대 약 78/89ms, 새 인스턴스 약 2,203ms였다. 이는 k6 전체 실행 p99와 다른 지표이며 서로 같은 값으로 비교하지 않는다. 느린 응답이 신규 노드에 집중된 것은 확인했지만, JIT·GC·연결 초기화 중 무엇 때문인지는 추가 분석이 필요하다.

기존·신규 컨테이너는 CPU quota 제한 없음, 메모리 제한 1,572,864,000 bytes, SPRING_PROFILES_ACTIVE=prod로 같았다. EC2는 모두 t3.small/unlimited였다. 다만 신규/기존의 CPU 크레딧 잔액까지 동일하게 맞춘 시험은 아니다.

## 판단과 다음 작업

- 3대가 후단 적체와 완료 시간을 줄이는 데 도움이 된다는 근거를 얻었다. 실서비스의 기본 용량을 선택할 때 참고할 수 있다.
- 시작 전에 단순히 150초 대기하는 것과 실제 참여 경로를 준비시키는 것은 다르다. #115에서 신규 노드에 실제 요청을 미리 처리시키는 방식과 첫 요청 구간을 검증해야 한다.
- drain에서는 세 앱 모두 claim 평균 약 1.4~1.6ms를 순차적으로 기다렸다. 서버 수를 늘려도 건별 왕복 구조는 남아 있어 #114의 작은 batch claim 비교는 여전히 의미가 있다.
- 워밍업 조건 변경과 batch claim 변경은 같은 실험에 섞지 않는다. 각 변경의 효과를 분리한다.

시험 구간의 단순 인스턴스×시간은 2대 약 714 instance-seconds, 3대 약 672 instance-seconds다. 이는 부팅/배포 대기, 실행 전후 유지 시간, CPU surplus, DB/Redis/ALB 비용을 뺀 처리 구간 참고값이다. 실제 청구액 절감으로 해석하지 않는다. 순간 앱 수와 실행 시간이 모두 비용에 영향을 준다.
