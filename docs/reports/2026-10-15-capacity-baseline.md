# 지속 RPS 탐색: 접수와 최종 처리의 간격

> 실행: 2026-10-15, AWS `ap-northeast-2` 테스트 환경
> 기준 코드·배포 이미지: `89902c3d8c86164fc03afef3f04738b65dab68ec`
> 목적: 지속 가능한 RPS를 확정하기 전, 유입률별 Queue·후단 처리·지연의 변화를 탐색한다. **최종 성능 PASS/FAIL 또는 정합성 PASS 보고서가 아니다.**

## 실험 조건

- 앱은 부하 중 `t3.small` 2대였다. ASG min 2 / max 3이며 세 번째 인스턴스의 scale-out은 부하 종료 후인 18:13:18 KST에 시작해 18:17:19 KST에 InService가 됐다. 따라서 세 번째 인스턴스의 효과를 이번 부하 처리량에 포함하지 않는다.
- 부하 발생기: `terraform-mcp` EC2의 k6 1.7.1. 캠페인별 초기 재고는 9,999,999건으로 테스트 중 재고가 소진되지 않았다.
- 도구·경로 점검: 캠페인 73, 목표 1,000 RPS를 60초 유지, 최대 3,000 VU.
- 단계별 탐색: 캠페인 74, 목표 2,000 → 3,000 → 4,000 RPS, 각 단계 ramp 15초·유지 60초, 최대 8,000 VU. **같은 실행의 다음 단계는 앞 단계에서 쌓인 Queue의 영향을 받으므로 독립 실험으로 보지 않는다.**
- 원본 k6·Redis·Prometheus 결과는 로컬 `evidence/20261015T0902Z-capacity-1k/`와 `evidence/20261015T0909Z-capacity-stages-2k-4k/`에 있다. `evidence/`는 Git에서 제외돼 PR에 포함되지 않는다.

## 관측 결과

| 목표 유입 | 단계 끝 근처 API 요청률¹ | DB 성공 경로 처리율¹ | Redis Queue 증가율² | 서버측 API p95/p99¹ |
| --- | ---: | ---: | ---: | ---: |
| 2,000 RPS | 약 1,986건/s | 약 1,158건/s | 약 970건/s | 7 / 45 ms |
| 3,000 RPS | 약 3,000건/s | 약 961건/s | 약 2,059건/s | 65 / 197 ms |
| 4,000 RPS | 약 2,591건/s | 약 360건/s | 약 2,321건/s | 1,340 / 2,715 ms |

¹ 단계 유지 종료 직전의 Prometheus 10초 샘플에서 구한 **직전 1분 이동평균**이다. 단계 전체 평균이나 k6 클라이언트 지연이 아니다. API는 참여 요청의 `http_server_requests_seconds_count`, DB 성공 경로는 `consumer_db_committed_total`의 `rate(...[1m])`를 사용했다. 특히 4,000 RPS 구간에는 앱 메트릭 scrape 공백 가능성이 있어 서버측 지연·처리율을 정밀한 최대치로 사용하지 않는다. `consumer_db_committed_total`은 물리적 신규 INSERT 건수와도 다르다.

² Redis 직접 `LLEN` 감시의 구간별 시작·끝 차이를 초로 나눈 값이다. 감시는 18:09:35 KST에 시작했으므로 첫 단계의 초기 38초는 빠져 있다. 각 구간은 각각 18:09:40~18:10:12, 18:10:27~18:11:27, 18:11:42~18:12:42 KST이다.

- **1,000 RPS 점검:** `202` 67,999건, `dropped_iterations=0`, HTTP 실패·5xx 0건, 전체 실행의 k6 클라이언트 p95/p99 43/133 ms. 캠페인 상태 API의 성공 건수와 재고 감소량은 접수 수와 일치했다. 그러나 Redis 직접 감시는 부하 종료 뒤에 시작했고 Prometheus Queue Gauge에서 최대 11,711건이 관측됐다. 60초 점검만으로 **1,000 RPS가 장시간 지속 가능하다**고 판단하지 않는다.
- **2,000~4,000 RPS 탐색:** `202` 585,658건, HTTP 실패·5xx 0건. k6 전체 실행 클라이언트 p95/p99는 3,235/15,422 ms. `dropped_iterations=70,090`은 목표 시각에 시작하지 못한 요청이며 API의 거절 70,090건이 아니다. 최대 8,000 VU에 도달했으므로 특히 **목표 4,000 RPS의 성패는 판정 불가**다.
- Redis Queue 직접 관측 최고값은 383,633건(18:12:49 KST)이었다. 신규 부하가 끝난 뒤 18:17:00 KST에 `LLEN=0`을 확인했다. 최종 Kafka consumer group lag는 0이었다.
- 캠페인 74 상태 API는 `successCount=585658`, `failCount=0`, `currentStock=9414341`을 반환했다. **DB 직접 row count·중복 검사와 접수→DB 반영 p95/p99는 수행·측정하지 않았으므로 최종 E2E 정합성 PASS는 선언하지 않는다.**
- Hikari pending은 단계 종료 근처 표본에서 0이었다. Kafka lag도 지속적 최대 병목으로 보이지 않았으나, 이것만으로 병목 위치를 확정하지 않는다. Grafana에서 일부 앱 CPU가 90%대에 오른 모습이 관측됐고, 고부하 시 메트릭 scrape 공백이 있어 정확한 최고 CPU는 미확정이다.

## 현재 결론과 판정 범위

2,000 RPS 단계부터 Redis Queue가 계속 증가했다. 따라서 **현재 2대 구성에서 2,000 RPS 이상의 End-to-End 지속 가능성은 입증되지 않았다.** 1,000 RPS도 짧은 실행과 Queue 관측 제한 때문에 안전한 상한으로 확정할 수 없다. 4,000 RPS는 부하 생성기의 dropped iterations까지 겹쳐 서비스 성능의 단독 실패로 판정하지 않는다.

`202` 접수 속도와 최종 DB 반영 속도는 다른 능력이다. 유한한 순간 폭주에서 Queue가 피크를 흡수하고 나중에 비워지는 것은 유효한 설계일 수 있지만, 계속 유입되는 트래픽에서는 Queue 증가 기울기가 0에 가까워져야 한다. 이번 결과는 API·Bridge·Consumer의 자원 경쟁 가능성을 보여 주지만, **어느 한 컴포넌트가 원인인지 또는 전면 재설계가 필요한지는 증명하지 않는다.**

## 다음 실행 계획

1. **운영 목표를 먼저 분리해 합의한다.** 총량 테스트는 목표 건수, 허용 접수 지연, 최대 Queue, 사후 drain 완료 시간, 최종 DB 정합성을 정한다. 지속 RPS 테스트는 목표 RPS·유지 시간·API p95/p99·Queue/lag 안정성·E2E 반영 지연을 별도로 정한다. 두 테스트가 같은 피크 RPS를 만족할 필요는 없다.
2. **높은 단계 반복 대신 평형점을 탐색한다.** 예를 들어 단일 캠페인·단일 목표 500/750/1,000 RPS를 각각 5~10분 유지한다. 수치는 탐색용이지 합격선이 아니다. Queue 감시를 부하 전에 시작하고, 매 실행에서 신규 캠페인과 동일한 앱 대수·사양·부하 발생기 조건을 사용한다. ASG 변경이 일어나면 고정 용량 비교를 보류한다.
3. **증거를 완성한다.** k6 `dropped_iterations=0`과 실제 유입률, API/Bridge/DB 각 처리율, Queue 기울기·oldest age, Kafka lag, 인스턴스별 CPU, Hikari pending, 종료 후 drain·DB row count·중복·재고를 확인한다. 접수→DB 완료 지연은 계측을 도입하기 전까지 미측정으로 표기한다. 같은 조건을 반복하지 못하면 지속 가능한 최대 RPS를 확정하지 않는다.
4. **목표와 측정치의 차이가 확인되면 한 변수씩 개선한다.** 로그·Consumer/JDBC 설정, API와 Worker 자원 분리, Bridge 왕복 비용을 순서대로 가설 검증한다. 성능 변경과 Redis pop→Kafka 발행 사이의 유실 복구 설계는 한 PR에 섞지 않는다. 개선 뒤에는 동일 조건의 capacity A/B와 별도의 150만 건 integrity 검증을 수행한다.
