# 30만 건에서 확인한 Bridge 처리 지연

> 2026-11-03 KST. 캠페인 107. 앱·테스트 스크립트 5b110eb(PR #118 머지).
> 앱 2대 t3.small, Kafka 3대, Redis 3 master. ASG desired 2/max 3 유지, 실행 중 증설 없음.
> 결과: 30만 건 응답·DB 정합성 확인. 개선할 구간은 확인했지만 아직 최적화 코드는 적용하지 않았다.

## 무엇을 확인하려고 했나

150만 r4에서 요청이 끝난 뒤에도 Bridge가 느려지는 이유를 찾기 위해, 요청 유입 중과 남은 Queue 처리 중을 분리해서 관측했다. 기존 run-test.sh prod integrity(shared-iterations)로 30만 건·500 VU, 최대 부하 시간 360초를 설정했다. 한 번의 총량 시험이며 지속 RPS 검증이나 과거 r4와의 동일 조건 A/B가 아니다.

계측은 5초마다 시작했으며 실제 수집 간격은 약 5~6초다. Queue·in-flight·master 메모리는 Redis 직접 조회, 호출 시간·CPU 등은 Prometheus에서 수집했다. Redis 메모리가 약 342MB를 넘으면 k6 프로세스 그룹을 중단하는 가드를 뒀지만 발동하지 않았다. 기존 데이터는 삭제하지 않았다.

부하 실행부터 최종 확인까지 약 357초였다. k6 요청 실행 시간은 약 107초이며 준비·종료 감지 시간과 구분한다. 1회 관측 요청률을 지속 가능한 RPS로 확정하지 않는다. ASG 정책·앱 사양·Lua·배치 크기는 변경하지 않았다.

## 이번에 구분한 두 문제

Prometheus의 스크래핑 지연과 구간 경계 영향을 줄이려고 유입 중은 시작 약 22~97초, drain은 부하 종료 감지 후 약 33~225초를 비교했다. 수치는 각 구간의 counter 차이/호출 수로 계산한 가중 평균이다.

| 구간 | 유입 중 | drain 중 |
| --- | ---: | ---: |
| Bridge Kafka 발행률 | 약 199건/s | 약 1,168건/s |
| 앱 2a CPU 평균 | 97.9% | 38.6% |
| 앱 2b CPU 평균 | 95.7% | 33.4% |
| Redis claim 평균, 2a | 27.56ms | 1.505ms |
| Redis claim 평균, 2b | 5.73ms | 1.614ms |
| Kafka send 동기 평균, 2a | 0.499ms | 0.033ms |
| Kafka send 동기 평균, 2b | 0.239ms | 0.024ms |

### 1. 요청이 몰릴 때 후단 처리가 크게 밀린다

요청이 몰릴 때 CPU가 거의 꽉 찼고 claim 호출도 길어졌다. 요청이 끝난 뒤 CPU와 claim 시간이 함께 내려가고 발행률은 약 5.9배로 상승했다. 요청과 후단 처리가 같은 앱·Redis 경로를 함께 쓰는 영향이 관측됐다. 다만 CPU 대기, Lettuce 연결/이벤트 루프 대기, 네트워크를 따로 계측하지 않았으므로 이 중 하나를 유일한 원인으로 지목하지 않는다.

### 2. 요청이 끝나도 한 건씩 기다리는 구조가 처리 속도를 제한한다

drain 구간에는 CPU 여유가 있었지만 한 건을 claim할 때마다 평균 약 1.5~1.6ms를 기다렸다. 이 호출 시간 합은 Bridge drain 회차 시간 합의 약 96.8~97.4%였다. Kafka send 동기 대기는 약 0.02~0.03ms였다.

따라서 다음 변경은 **여러 건을 작은 묶음으로 안전하게 claim해 왕복 횟수를 줄이는 방식**을 먼저 비교하는 것이 타당하다. 이 97%는 Redis CPU 사용률이 아니라 앱이 해당 호출 구간에서 보낸 시간의 비율이다. 타이머의 완료 시점과 스크래핑 시점이 달라 비율은 근삿값이다. 유입 구간에서는 긴 미완료 회차 때문에 비율이 100%를 넘었으므로 그 비율을 해석하지 않았다.

## 추가 확인과 남은 의문

- 드레인 중 ACK 평균 약 1.4~1.6ms도 관측했다. ACK는 별도 실행기에서 처리하므로 claim 시간과 그대로 합산하지 않는다. 최종 publish/ACK count 합계는 각각 30만이었다.
- Redis SLOWLOG에는 일부 EVALSHA·SET이 10~55ms 걸린 기록이 있었다. 원문 인자 없이 시각·명령명·시간만 보관했다. 이를 근거로 모든 지연이 네트워크라고 단정하지 않는다. LATENCY LATEST는 빈 값이었고, 모니터링 설정을 확인하지 않아 장애가 없었다는 증거로 쓰지 않는다.
- CloudWatch에서 조회한 이전 r4 구간과 이번 구간의 반환 샘플에는 Redis 네트워크 대역폭·패킷 한도 초과, TrafficManagementActive의 양수 값이 없었다. 수집 해상도·지연 한계가 있어 네트워크 지연 자체를 배제하는 결과는 아니다.
- 이전 150만 시험에서 drain 중 처리량이 절반으로 떨어진 현상은 이번 약 4분 drain에서 동일하게 재현하지 못했다. 장시간 동작과 150만 같은 조건의 비교는 남아 있다.

## 다음 작업

한 번에 가져오는 claim 수를 작게 제한한 구현을 로컬에서 먼저 검증한다. in-flight 상한·원본 보존·고유 token·늦은 ACK·만료 복구를 유지하고 Lua가 Redis를 오래 점유하지 않는지도 확인한다. 이후 같은 앱 2대·30만·500 VU 조건으로 API p95/p99, 발행률, 최대 Queue, 메모리, drain을 함께 비교한다. drain만 빨라지고 API 지연이 나빠지는 결과도 숨기지 않는다.

이 기록으로 #114를 종료하지 않는다. 서버는 켜 둔 상태이며 기존 데이터 삭제·env-down은 하지 않았다. 새 캠페인의 참여 키는 남아 있어 다음 대규모 시험 전에 잔류 메모리를 다시 확인해야 한다.
