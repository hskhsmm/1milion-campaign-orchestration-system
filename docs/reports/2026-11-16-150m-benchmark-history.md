# 150만 건 부하 시험 비교

- ¹ k6의 초당 HTTP 202 집계를 우선 사용했다. 11월 7~10일 보고서에는 k6 반복률로 기재돼 있고 해당 회차는 150만 건 모두 202였다. 9월 20일의 5,336건/s는 Prometheus 1분 피크라 평균 열에는 넣지 않았다.
- ² 10월 13일은 보고서의 202 건수를 k6 소요 시간 485.6초 / 458.8초로 나눈 값이다. 당시 표의 3,295 / 3,487건/s는 160만 요청 기준이다. 11월 2일은 로컬 r4 보고서의 평균 반복률 3,154.5건/s에 202 비율 1,499,978 / 1,500,000을 적용했다. r3·r4의 종료 후 드레인 603 / 911초는 [11월 3일 드레인 분석](2026-11-03-bridge-drain-300k.md)에도 기록돼 있다.
- ³ 10월 13일 값은 재고 소진 시점의 LLEN이다. 다른 회차의 구간 최대치와 구분했다. 표의 `—`는 같은 지표로 확인할 값이 없는 경우다.
- 160만 회차의 클라이언트 p95에는 재고 소진 응답이 포함된다. 11월 7~10일 실험과 최신 회차의 스크립트 범위, 서버 교체·예열, Redis 초기 상태도 일부 다르다. 이 표는 회차별 관측을 비교하며, 특정 변경 하나의 개선율을 추정하는 A/B 자료로 쓰지 않는다.

## 접수 이후 달라진 점

9월 19일과 25일에는 재고 소진 뒤 캠페인이 활성 목록에서 빠져 대기열 약 130만 건이 고립되었다. 9월 28일의 정상 완주와 강제 합류 재현은 결과가 달라 표에는 완주 회차 63을 넣었다. [9월 28일 원인 추적](2026-09-28-zombie-container-root-cause.md)

9월 20일에는 요청이 밀려들 때 API가 약 5,000~5,336건/s를 접수하는 동안 Bridge는 대표 표본에서 약 1,660건/s를 발행했다. 11월 2일 r4에서도 Redis Queue가 약 125만 건까지 쌓였고, k6가 끝난 뒤 Queue·in-flight·lag가 모두 0이 되기까지 911초가 걸렸다. [9월 20일 보고서](2026-09-20-aws-recovery-150m-validation.md) · [r4 후속 분석](2026-11-03-bridge-drain-300k.md)

11월 15일 603에서는 요청을 받는 동안 API·Bridge·Consumer가 약 5,000건/s 수준을 함께 처리했고, 최대 Queue 관측은 5,439건이었다. k6 종료를 기록한 18:29:00 KST 이후 첫 완전 배출 표본에서 Queue·in-flight·lag가 모두 0이었다. 표본 주기와 시작·종료 지표의 정의가 달라 과거 드레인 시간과 초 단위 개선율은 계산하지 않았다. 현재 구성의 성과는 **유입 중에 후단이 따라가고, 끝날 때 큰 적체를 남기지 않은 것**이다.
