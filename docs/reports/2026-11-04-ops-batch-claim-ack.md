### 2-1. N=1에서도 drain이 빨라진 이유 (116 → 115)

- 같은 env에서 PR #120 전 이미지(116)를 다시 배포해 비교했다. 116 ≈ 107이므로 env·날짜·Redis 상태 차이로는 설명되지 않는다.
- N=1 경로의 Java 코드는 같다(같은 단건 Lua·반복문). 남은 동작 차이는 `application.yml`의 Lettuce `timeout: 2s`와 cluster topology refresh다. 개선은 클라이언트 측 claim 호출 시간(1.45 → 0.64ms)에서 나타났다.
- **원인은 추정**이다. 메커니즘은 확인하지 않았다. refresh만 끈 실행이 필요하다.
- ElastiCache CPU 크레딧(10~18 잔여, 엔진 CPU 최대 약 25%)과 앱 EC2 크레딧(`unlimited`, surplus 0)은 원인 후보에서 제외했다.

### 2-2. N=10에서 ACK 병목 (117)

- 하네스 형식의 기존 판정은 DB 건수만 보고 PASS를 냈다. 그러나 ACK 실행기(`ThreadPoolExecutor(4, 4)`, 큐 2,048, `AbortPolicy`)가 포화돼 **ACK 7,157건이 거부**됐다.
- 거부된 claim이 in-flight에 남아 상한 10,000 근처(9,987)에 닿았고 claim이 멈췄다. drain 구간 앱 CPU는 0.02였다.
- lease 5분 만료 후 reclaim → 중복 발행 7,157건 → Consumer 중복 INSERT 데드락(51건) → 배치 재시도로 이어졌다. DB 고유 제약으로 최종 건수는 맞았다.
- 원인 계산: 부하 중 ACK 1건 ≈ 1.9ms라 처리 상한이 앱당 약 2,100건/s다. N=10에서 발행은 순간 약 5,900건/s(2대 합)였다.
- 수정은 [ACK 묶음 처리](2026-11-04-bridge-ack-batch.md)다(PR #122).

### 2-3. 묶음 ACK 후 (118)

- **ACK 병목은 해소됐다**: 발행 = ACK removed = 300,000, 거부·reclaim·not_found·error 0, 역압 발동 0. ACK Redis 호출 39,434회(평균 6.4~9.5건/회).
- **전체 완료가 빨라졌다**: Bridge가 접수를 거의 실시간으로 따라가 부하 종료 후 5초에 발행이 끝났다(N=1 85초). 접수 시작 → 발행 완료 195 → 125초.
- **대가로 API 지연이 늘었다**: 서버 p99 407 → 659ms, k6 처리율 2,926 → 2,333 iter/s(닫힌 모델이라 지연과 함께 감소).
  - 캠페인 샤드 Redis 엔진 CPU는 1분 최대 21%(115는 25%)라 Redis 병목이 아니다.
  - Bridge 작업(직렬화·Kafka send·콜백)이 부하 종료 후가 아니라 접수와 동시에 같은 앱 CPU(0.9 이상)를 쓴 결과로 **추정**한다. 총 작업량은 같고 시점이 앞당겨졌다.

## 4. scale-out (캠페인 122, `6f3fa37` N=10, 120만 건)

- 앱 2대에서 시작했다. k6 시작 22:49:52 → 22:49:53 `set-desired-capacity 3` → 새 인스턴스(CodeDeploy로 `6f3fa37`·N=10 수신) → 22:51:59 ALB healthy.

| 항목 | 값 |
| --- | --- |
| 202 / DB / 중복 / 5xx·timeout | 1,200,000 / 1,200,000 / 0 / 0 |
| 발행 / reclaim / ACK 거부 | 1,200,000 / 0 / 0 (새 인스턴스 발행 63,999) |
| 부하 종료 → Queue·in-flight·lag 0 | 11초 |
| 2대 (합류 전) | 202 약 4,450/s, 서버 p99 약 280ms |
| **합류 직후 약 1분** | 202 약 2,000~2,800/s(최저 1,992), p99 870~1,005ms |
| 3대 (회복 후) | 202 4,800~5,300/s, p99 340~380ms |

- N=10·묶음 ACK에서 인스턴스가 늘어도 전달 정합성이 유지된다.
- 합류 직후 처리율 저하·p99 상승은 [앱 2대·3대 비교](2026-11-03-app-2-vs-3-300k.md)·[재시험](2026-11-03-app-warm-repeat-300k.md)에서 본 신규 인스턴스 현상과 같다(ALB 즉시 투입, JVM 워밍업 전). 이전 150만 실행에서도 scale-out 직후 같은 징후가 있었다. batch claim·묶음 ACK와 무관하다. 이번에는 timeout이 0이었다.
- 선행 실행 두 건은 무효로 처리했다.
  - 120: 90만 건, 사용자 요청으로 중단. 접수 666,503 = DB.
  - 121: 중단 직후 늦게 발동한 step 알람(CPU ≥ 80% 2분)으로 이미 3대인 상태에서 시작해 중단. 접수 261,818 = DB. 세 번째 인스턴스를 지정 종료하고 2대에서 다시 했다.

## 5. 판정 보강

DB 고유 제약은 Kafka 중복 발행을 숨긴다. 그래서 정상 integrity 시험의 기대값에 **발행 수 = 202, reclaim 0, ACK 거부 0**을 추가했다(운영 PC 판정 스크립트). 이 기준으로 다시 판정하면 117은 FAIL이고 115·116·118은 PASS다.

## 6. 미검증과 남은 위험

- Lettuce 설정이 N=1 drain 개선의 원인인지(refresh만 끈 실행)
- N=50 (앱 CPU가 이미 한계라 이득이 작을 것으로 보고 보류)
- N=10 + 150만·200만, 다중 캠페인 동시 진행
- 앱 정상 종료(배포·scale-in) 시 메모리의 대기 ACK 유실 → 5분 뒤 중복 발행. 강제 종료는 기존과 같은 reclaim 경로
- 역압이 앱 인스턴스 전체 기준이라, 다중 캠페인 중 한 샤드가 느려지면 다른 캠페인의 claim도 쉴 수 있음
- API와 Bridge·Consumer의 CPU 공유(118의 p99 증가), 차가운 JVM 합류
- 운영 기본 N: 지금 운영은 N=10이다(API 꼬리 지연 대 전체 완료 시간). 결정은 [다음 작업](../plans/performance-next-steps.md)에서 다룬다.
