# 성능·안정성 조사 종합 (2026-11-07 ~ 11-11)

API·워커 분리(PR #124) 뒤 "분리하면 더 빨라지는가"를 재다가, 가상 스레드 설정, 서버 동결, Consumer 장애까지 이어진 조사를 한 장으로 정리했다. 자세한 수치와 근거는 각 보고서에 있다.

## 결론

1. **t3.small(2 vCPU)에서는 가상 스레드를 끈다.** 콜드 3,000 RPS, 예열 5,000 RPS, 150만 건을 모두 통과한 유일한 설정이고 메모리도 가장 적게 쓴다.
2. **가상 스레드 켬이 고부하에서 무너지는 근본 원인은 CPU 포화와 동시 처리 상한 부재다.** 캐리어 수(2·4·8)를 바꿔도 5,000 RPS에서는 똑같이 무너진다.
3. **API·워커 분리는 지금 설정에서 공용 3대보다 못하다. 공용 3대를 유지한다.** 워커 1대의 Bridge 발행 상한(약 3,460건/s) 때문에 30만 건 처리가 54% 늦다.
4. **부하 시험 중 Consumer가 같은 배치를 영원히 재시도하는 결함을 찾아 고쳤다.** 같은 장애를 AWS에서 다시 일으켜 수정 전·후를 비교했고, 미반영이 201건에서 0건이 됐다.
5. **Kafka 디스크가 시험 데이터로 가득 찰 수 있다.** 보관 7일, 디스크 8GB라 이틀 시험으로 브로커 1대가 멈췄다.

## 주제별 핵심

### 가상 스레드 켬 vs 끔

| | 켬 (캐리어 2, 기본값) | 켬 (캐리어 8) | 끔 |
| --- | --- | --- | --- |
| 콜드 3,000 RPS | VALID 0/10 (+ 11-11 재측정 0/1) | VALID 3/3 | VALID 3/3 |
| 예열 5,000 RPS | FAIL·INCONCLUSIVE | INCONCLUSIVE 2/2 (11-10, 11-11 재측정 모두) | 11-09 VALID 3/3, 11-11 VALID 4/7 (미달 회차도 dropped 0.2% 이하, 5xx 0) |
| 메모리 | 1대 약 1.4GB까지 | 힙이 끔의 2~4배 | 가장 적음 |

끔의 5,000 RPS는 오늘 7회 중 4회 VALID로, **한계 바로 근처**다. 단계 시험(5,000 → 6,000 → 7,000)도 5,000에서 멈췄다.

### 가상 스레드 켬이 5,000 RPS에서 무너지는 이유

켬 c8·c4 4회, 5,000 RPS가 무너지기 전 60초를 미리 정한 판정표로 봤다.

| 증거 | 3,000 RPS | 5,000 RPS |
| --- | --- | --- |
| 캐리어가 OS CPU를 기다린 시간 | 캐리어당 68~171ms/s | **365~567ms/s** (실행 시간보다 김) |
| 캐리어를 기다리는 가상 스레드 수 | 최대 4~243 | **최대 476~5,462** |
| 요청 시간 중 Redis가 차지한 몫 | | c8 33~38%, c4 6~21% (Redis는 빠른데 요청이 느림) |
| Lettuce 스레드 CPU | 약 10% | 6~13% (병목 아님) |
| 캐리어 4 vs 8 | | 둘 다 4/4 메모리 고갈 |

**해석:** 2 vCPU가 포화되면 캐리어가 CPU를 기다리고, 그 사이 가상 스레드는 캐리어를 기다리며 쌓인다. 켬은 요청 수 상한이 없어 몰린 만큼 서버 안에 쌓이고, 메모리가 바닥나 동결된다. 끔은 Tomcat 스레드 200개에서 막혀, 넘친 요청이 서버 밖 연결 대기열에서 기다리므로 무너지지 않는다. 캐리어 수를 바꿔도 같으므로 "캐리어가 너무 많다"는 가설은 기각했다.

**Lettuce 락 대기 (정황상 지지, 직접 확인은 못 함):** Lettuce 이벤트 루프와 Tomcat Poller가 기다린 락 1,473건 중 97%를 가상 스레드가 잡고 있었다. 가장 길게 기다린 순간 8번 중 7번은 캐리어 2개가 모두 사용 중이었고, 대기 가상 스레드가 164~1,979개였다(평소 0~1개). 락을 잡은 가상 스레드가 캐리어를 못 얻어 늦게 놓았다는 설명과 맞는다. 다만 이를 직접 보여 줄 스레드 덤프가 수집 스크립트 결함으로 남지 않아 판정은 보류했다.

### 한 대만 먼저 느려지는 이유 (미해결)

서버 3대 중 1대만 응답 꼬리가 2~4배 긴 현상이 켬·끔 모두에서 보인다. 10회 동안 부하 시작 첫 10초의 지표 6개(C2 컴파일, 캐리어 CPU·대기, 수신 패킷, Lettuce CPU·대기)를 비교했지만, 먼저 느려진 서버를 미리 알려 주는 지표는 없었다(기준 7/10, 최대 6/10). AZ, 하네스 관리 요청, 로그 양 등 다른 후보도 기각했다.

새로 본 점: **같은 서버 묶음 안에서는 느린 서버가 바뀌지 않는다**(2-b 3회 모두 같은 서버, A/B 2차 A 확인 회차 모두 같은 서버). 서버(호스트) 자체 요인일 수 있다. 다음 시험에서 CPU steal을 기록해야 판정할 수 있다.

### API·워커 분리 A/B 2차

| 기준 (A로 미리 고정) | A 공용 3대 | B API 2 + 워커 1 | 결과 |
| --- | ---: | ---: | --- |
| 3,000 RPS k6 p99 중앙값 | 69.1ms | 126.8ms | 개선 아님 (+84%) |
| 3,000 RPS k6 p95 중앙값 | 25.1ms | 33.1ms | 미달 (+32%) |
| 30만 건 첫 요청 → 마지막 DB | 59.0초 | 91.0초 | 미달 (+54%) |

- **30만 건이 늦은 이유 (확정):** Bridge는 100ms 쉬고 1,000건을 10건씩 순서대로 Redis에서 가져온다. 워커 1대로 계산한 상한 약 3,460건/s가 측정값 3,457건/s와 같다. 워커 CPU는 30%만 써서, 하드웨어가 아니라 Bridge 구조의 상한이다. DB·Consumer는 병목이 아니었다.
- **응답 꼬리가 긴 이유:** 위의 "느린 서버 1대"가 받는 몫이 A는 1/3, B는 1/2이다. 같은 역할 서버끼리는 요청이 1.5배여도 처리 시간이 거의 같다.

### Consumer 무한 재시도 결함

앱이 강제 종료되면 Bridge가 확인(ACK)하지 못한 이벤트를 5분 뒤 다시 발행한다(설계상 최소 1회 전달). 이번에는 Consumer도 같이 죽어 있어서 원본과 사본이 같은 배치에 들어갔고, `rewriteBatchedStatements`가 합친 INSERT 한 문장 안의 중복에 MySQL이 1869 오류를 냈다. Consumer는 이를 일시적 DB 실패로 보고 배치를 nack해서 영원히 다시 실패했다.

| | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 1869 오류 (재기동 후 10분) | 2,718건 | 0건 |
| Kafka lag | 221에서 정지 | 0 |
| 접수 대비 DB 미반영 | 201건 | 0건 |

수정은 INSERT 전에 배치 안의 `(campaign_id, user_id)` 중복을 거르는 것이다.

### 측정 도구가 결과에 준 영향

11-10 밤에는 원인을 찾으려고 기록 도구를 더 켰다(상주 스케줄러 표본기, Tomcat MBean, `ThreadPark` 기록). 11-11에 11-09 조건 그대로 다시 쟀다.

| 조건 | 11-10 밤 (추가 도구) | 11-11 재측정 (11-09 도구) | 11-09 |
| --- | --- | --- | --- |
| 켬 c8 5,000 | 4/4 메모리 고갈 | INCONCLUSIVE 2, 동결 0 | INCONCLUSIVE 2 |
| 끔 5,000 | VALID 3/4 | VALID 1/2 | VALID 3/3 |
| 켬 c2 콜드 3,000 | FAIL 3 | INCONCLUSIVE 1 | VALID 0/10 |

켬의 메모리 고갈은 추가 도구 영향이 컸다고 본다. 끔 5,000의 편차는 도구를 맞춰도 남아서, 도구보다 회차 편차와 환경(서버 배치·호스트) 쪽이다. 판정 패턴 자체는 세 날 모두 같다.
