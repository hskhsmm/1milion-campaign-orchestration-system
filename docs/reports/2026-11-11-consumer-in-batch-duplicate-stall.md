# Consumer 무한 재시도 장애: 묶음 안 중복과 MySQL 1869 (2026-11-11)

부하 시험 중 Kafka Consumer가 같은 배치를 끝없이 다시 시도하며 파티션 6개가 멈췄다. 원인을 실제 메시지·로그·DB로 확정하고, 별도 MySQL에서 재현한 뒤, AWS에서 장애를 다시 일으켜 수정 전·후를 비교했다. 시험 환경의 시험 캠페인에서 일어난 일이며 실제 사용자 데이터는 없다.

## 한눈에 보기

**원인:** 앱이 강제 종료된 뒤 Bridge가 "Kafka에는 보냈지만 Redis 확인(ACK)을 못 한" 이벤트 10건을 다시 발행했다. 소비가 멈춰 있던 탓에 원본과 사본이 **같은 Consumer 배치(100건)** 에 들어갔다. `rewriteBatchedStatements=true`가 100건을 INSERT 문장 하나로 합치는데, MySQL은 한 문장 안에서 방금 만든 행에 `ON DUPLICATE KEY UPDATE id = id`가 걸리면 **1869 오류**로 문장 전체를 거부한다. Consumer는 이를 일시적 DB 실패로 보고 배치를 nack해서, 같은 배치가 1초마다 영원히 다시 실패했다.

**수정:** INSERT 전에 배치 안의 `(campaign_id, user_id)` 중복을 첫 건만 남기고 거른다.

**검증 (AWS, 같은 장애를 두 번 주입):**

| --- | ---: | ---: |

## 원인 분석

### 1. 막힌 배치에 같은 메시지가 두 번 들어 있었다 (확정)

막힌 6개 파티션의 커밋 위치부터 100건씩, 총 600건을 Kafka에서 직접 읽었다. 6개 배치 모두 같은 `(캠페인, 사용자, sequence)`가 1~2쌍씩 들어 있었다.

| 파티션 | 중복 쌍 | 원본 → 사본 위치 차이 |
| --- | ---: | --- |
| 1 | 1 | 14칸 |
| 2 | 2 | 10·12칸 |
| 4 | 1 | 19칸 |
| 5 | 2 | 21·23칸 |
| 6 | 2 | 25·27칸 |
| 9 | 2 | 19·21칸 |

- 중복은 정확히 **10건**이고, 캠페인 497의 sequence **249038~249047**(연속)이다. 운영 Bridge의 claim 묶음 크기 `N=10`과 같다. **한 claim 묶음이 통째로 두 번 발행된 것이다.**
- sequence까지 같으므로 사용자가 두 번 참여한 것이 아니라 같은 이벤트의 사본이다.
- 원본 10건은 모두 03:40:16.465, 사본 10건은 모두 03:54:30.7에 만들어졌다.
- 앱이 모두 멈춰 그사이 새 발행이 없었기 때문에, 사본이 원본 바로 뒤(10~27칸)에 놓였다. 그래서 재기동 후 첫 100건 배치에 둘이 함께 들어갔다.
- DB에는 이 10개 sequence가 **0건**이다. 원본도 저장되지 못했다.

### 2. MySQL은 한 문장 안의 중복에만 1869를 낸다 (재현으로 확정)

Consumer의 저장 문장은 다음과 같다.

```sql
INSERT INTO participation_history (campaign_id, user_id, sequence, status, created_at, updated_at)
VALUES (?, ?, ?, 'SUCCESS', NOW(), NOW())
ON DUPLICATE KEY UPDATE id = id
```

운영 JDBC URL에 `rewriteBatchedStatements=true`가 있어서 `batchUpdate` 100건이 다중 행 INSERT 문장 하나로 바뀐다. 운영과 같은 MySQL 8.4(`innodb_autoinc_lock_mode=2`), 같은 표 구조로 시험했다.

| 경우 | 결과 |
| --- | --- |
| A. 한 문장 안에 "이미 저장된 행"의 중복 | 정상 (중복 무시) |
| C. 같은 새 행을 문장 2개로 따로 저장 | 정상 |
| **B. 같은 새 행이 한 다중 행 INSERT 안에 두 번** | **`ERROR 1869 (HY000): Auto-increment value in UPDATE conflicts with internally generated values`** |

B에서는 첫 행이 새 자동 번호를 받고, 같은 문장의 두 번째 행이 그 행과 충돌한다. 이때 `id = id`가 "이 문장이 방금 만든 자동 번호를 UPDATE로 다시 쓴다"로 판정되어 거부된다. 평소의 중복(A, 다른 배치에서 이미 저장된 행)은 문제없이 무시되므로, 이 경로는 원본과 사본이 **같은 배치**에 들어갈 때만 드러난다.

### 3. Consumer가 이 오류를 재시도 대상으로 분류했다 (확정)

`ParticipationEventConsumer.storeEvents`는 배치 INSERT의 예외를 둘로 나눈다.

- `DataIntegrityViolationException`: 행 단위로 다시 넣고, 그래도 거부되면 그 메시지만 DLQ로 보낸다.
- **그 밖의 예외: 메시지 탓이 아닌 DB 실패로 보고 배치 전체를 nack한다.**

1869는 Spring에서 `UncategorizedSQLException`(그 밖의 예외)으로 온다. 그래서 배치 전체를 nack하고, 같은 배치가 다시 와서 다시 실패했다. 재시작해도 커밋 위치가 같아서 계속됐다.

### 4. 왜 전에는 안 보였나 (추정)

같은 배치에 들어가려면 **사본이 발행될 때 원본이 아직 소비되지 않아야** 한다. 일부 서버만 죽으면 남은 서버의 Consumer가 claim lease(5분) 안에 원본을 소비하므로, 사본은 나중 배치에서 경우 A로 무시된다. 이번에는 메모리 보호 장치가 서버 3대를 모두 즉시 종료한 뒤 14분 동안 앱이 모두 꺼져 있다가 재기동되어 조건이 맞았다.

## 수정

`storeEvents`에서 INSERT 인자를 만들 때 `(campaign_id, user_id)`가 이미 나온 이벤트는 건너뛴다. `participation_history`의 고유 키는 `uk_campaign_user (campaign_id, user_id)` 하나뿐이라(마이그레이션 V1~V10 확인) 이 기준으로 충분하다. 거른 건수는 지표 `consumer.batch.in_batch_duplicates`와 WARN 로그로 남긴다. 거른 이벤트도 같은 행으로 저장된 것이므로 저장 건수에 포함하고 ACK한다(기존 "이미 있던 중복 포함" 의미와 같다).

- 브랜치: `fix/consumer-in-batch-duplicate` (`a6f8a02` 기준, 미커밋)
- 단위 테스트: 11-11 실측과 같은 형태(원본, 다른 이벤트, 사본)로 INSERT 인자 2건·ACK·nack 없음·지표 1을 확인하는 테스트 추가. `ParticipationEventConsumerTest` 8/8 통과.

## 검증 (AWS 장애 주입 A/B)

판정 기준은 실행 전에 정해 기록했다.

| 항목 | 값 |
| --- | --- |
| 구성 | 공용 3대, 가상 스레드 끔, 3,000 RPS 고정 도착률 |
| 장애 | 부하 시작 +90초에 **앱 3대 동시 `docker kill`**(OOM kill 흉내) → 6분 이상 정지(claim lease 5분 초과) → 같은 이미지로 재기동 → 10분 관찰 |
| 대조 | 현재 이미지 그대로 (`…@sha256:32fc3cfc6b03…`) |
| 수정 | 같은 이미지에서 `app.jar`만 수정본으로 바꾼 서버 로컬 이미지 (ECR·배포 파이프라인 미사용) |
| 대조 기준 | 재기동 뒤 1869 > 0 이고 lag가 0으로 안 내려가면 "재현됨" (재현 안 되면 수정 판정 불가) |
| 수정 합격 기준 | 1869 = 0, Queue·in-flight·lag = 0, DB 행 수 = 접수 수, 묶음 중복 지표 > 0 |

| | 대조 (캠페인 594) | 수정 (캠페인 597) |

| kill 시각 | 16:10:11 | 17:09:22 |
| 재발행 | 40건 (kill 때 in-flight) | 77건 (`Expired bridge claims returned to queue … count=77`) |
| 재기동 +30초 | 1869 114건, lag 80 → 221 | 1869 0, lag 0, 중복 제거 45건 (배치 10개에서 1~9건씩) |

## 함께 발견한 문제: Kafka 디스크 고갈

원인 조사 중 Kafka 브로커 `kafka-1`이 04:15에 멈춘 것을 발견했다. 콘솔에 "No space left on device"가 남아 있었다.

| 항목 | 값 |
| --- | --- |
| 디스크 | 브로커마다 루트 8GB, 토픽 데이터 약 5.6GB (파티션당 약 570MB) |
| 설정 | `log.retention.hours=168`(7일), `segment.bytes=1GB` → 시험 데이터가 거의 지워지지 않고 쌓임 |
| 상태 | kafka-1 정지, kafka-2 99%(남은 150MB), kafka-3 98%. `min.insync.replicas=2`라 한 대 더 멈추면 발행 전체가 멈추는 상태였다 |
| 조치 | 참여 토픽과 Consumer 그룹을 지우고 같은 설정으로 다시 만들었다. kafka-1은 디스크가 0이라 원격 명령도 안 되어, 볼륨을 다른 서버에 붙여 정리한 뒤 되돌렸다(볼륨 8 → 10GB) |
| 남은 일 | 보관 기간·크기 제한 설정, kafka-1 볼륨과 Terraform(`volume_size = 8`) 불일치 정리 |

이 문제는 소비 막힘의 원인이 아니다. 막힘은 03:56에 시작됐고 kafka-1은 04:15에 멈췄다. 밀린 42만 건도 전체 데이터의 1% 미만이다.

## 남은 위험과 미검증

- **수정 범위:** 배치 안 중복으로 인한 무한 재시도만 막는다. 같은 이벤트가 두 번 발행되는 것 자체(at-least-once)는 설계대로 남는다.
- **분류 방식:** 1869 외에 "메시지 탓인데 일시적 DB 실패로 분류되는" 다른 오류가 있으면 같은 무한 nack이 생길 수 있다. 이번에는 조사하지 않았다.
- **검증 범위:** AWS 검증은 1회 대조·1회 수정이다. 수정본은 로컬 빌드 jar이라 CI 빌드와 JDK가 다를 수 있다.
- **로그 보존:** 대조 회차와 03:54 재발행 컨테이너의 앱 원본 로그는 재기동으로 사라졌다. MySQL은 이 오류를 서버 로그에 남기지 않는다(RDS 에러 로그 0줄, `performance_schema` 꺼짐). 앱 로그가 유일한 원본이다.
