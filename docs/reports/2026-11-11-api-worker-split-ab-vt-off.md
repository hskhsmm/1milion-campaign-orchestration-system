# API·워커 분리 A/B 2차 결과: 가상 스레드 끔 (2026-11-11)

앱 서버 3대를 **공용 3대(A)** 로 쓸 때와 **API 2대 + 워커 1대(B)** 로 나눌 때를, 가상 스레드를 끈 설정(t3.small 기준 설정)으로 다시 비교했다. 1차 비교는 가상 스레드 켬이었다([1차 결과](2026-11-09-api-worker-split-ab.md)). 계획과 합격선은 [A/B 2차 계획](../plans/api-worker-split-ab-vt-off.md)에 있다.

## 한눈에 보기

**판정: B는 채택 기준 3개 모두 미달이다. t3.small·가상 스레드 끔에서는 공용 3대(A)를 유지한다.**

| 기준 (B 측정 전에 A 값으로 고정) | A | B | 결과 |
| --- | ---: | ---: | --- |
| 3,000 RPS k6 p99 중앙값: 55.3ms 미만이면서 A 최저 67.0ms 미만이면 개선 | 69.1ms | 126.8ms | **개선 아님** (+84%) |
| 3,000 RPS k6 p95 중앙값: 26.4ms 이하 | 25.1ms | 33.1ms | **미달** (+32%) |
| 30만 건 첫 요청 → 마지막 DB 중앙값: 62.0초 이하 | 59.0초 | 91.0초 | **미달** (+54%) |
| 정합성: 202 = 발행 = DB, 5xx·dropped·reclaim 0 | 6/6 회차 충족 | 6/6 회차 충족 | 통과 |

**왜 B가 느린가 (요약)**

| 결과 | 원인 | 근거의 강도 |
| --- | --- | --- |
| 30만 건이 54% 늦게 끝남 | 워커 1대의 **Bridge 발행 속도 상한(약 3,460건/s)**. DB·Consumer는 병목 아님 | 확정. 계산한 상한과 측정값이 일치 |
| 3,000 RPS 응답 꼬리가 길어짐 | 원래 있던 **"느린 서버 1대"** 가 받는 몫이 1/3에서 1/2로 커짐 | 수치로 확인. 느린 서버가 생기는 이유는 미해결 |

이 결과는 "분리 구조가 나쁘다"가 아니라 **"지금 설정의 워커 1대와 API 2대로는 공용 3대보다 못하다"** 는 뜻이다. 원인이 Bridge 설정값과 서버 대수라 조정 여지가 있다(아래 [개선 후보](#개선-후보-미검증)).

## 원인 1: 30만 건이 늦은 이유는 워커 1대의 Bridge 발행 상한이다 (확정)

### Bridge가 일하는 방식

Bridge는 Redis Queue의 참여 이벤트를 Kafka로 옮긴다. 앱 인스턴스마다 다음을 반복한다(`ParticipationBridge`).

1. 직전 회차가 끝나면 **100ms 쉰다** (`@Scheduled(fixedDelay = 100)`).
2. 캠페인마다 이번 회차에 가져갈 최대 건수를 Queue 길이로 정한다: 1만 건 미만 **500건**, 1만~10만 건 **1,000건**, 10만 건 이상 **2,000건**.
3. 그 건수를 **10건씩(N=10) Redis 호출 한 번으로** 가져온다. 호출은 **순서대로** 한다.
4. 가져온 이벤트를 Kafka로 비동기 발행한다.

그래서 인스턴스 하나의 발행 속도에는 상한이 있다.

> **상한 = 회차당 건수 ÷ (100ms + 호출 횟수 × Redis 호출 1회 시간)**

### 계산값과 측정값이 일치한다

B 워커의 Redis claim 호출은 평균 **1.79ms**다(30만 건 B-2, 부하 시작 +50초 구간).

| Queue 길이 | 회차당 건수 | 호출 횟수 | 회차 시간 | 계산 상한 | 측정 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1만 미만 | 500 | 50 | 100 + 90 = 190ms | **약 2,630건/s** | 3,000 RPS를 못 따라가 Queue가 1만을 넘을 때까지 쌓임 (B 3,000 Queue 최대 1.3만~1.4만) |
| 1만~10만 | 1,000 | 100 | 100 + 179 = 279ms (실측 289ms) | **약 3,460건/s** | 회차 3.47회/s, **발행 3,457건/s** |
| 10만 이상 | 2,000 | 200 | 100 + 358 = 458ms | 약 4,370건/s | 30만 건 Queue가 10만을 넘은 뒤 11만 안팎에서 멈춤 (최대 10.9만~11.4만) |

30만 건에서 202는 최대 약 5,500건/s로 들어오는데 워커 1대는 약 3,460건/s만 내보낸다. 그래서 Redis Queue가 10만 건 넘게 쌓이고, 접수가 끝난 뒤 이를 비우는 데 30초 이상 걸린다.

### DB·Consumer·하드웨어는 병목이 아니다

| 지표 (30만 건) | A | B | 해석 |
| --- | ---: | ---: | --- |
| Kafka 발행 속도 (안정 구간 중앙값) | 3,104~4,091건/s (3대 합) | 3,182~3,208건/s (1대) | B는 3,600 부근에서 평평하게 막힘 |
| Consumer 처리 = DB 반영 속도 | 발행과 같음 | 발행과 같음 | 소비는 발행을 바로 따라감 |
| Kafka lag 최대 | 617~9,609 | **182~233** | B는 Kafka에 거의 안 쌓임 → 소비 쪽 여유 |
| 워커 CPU 최대 | - | **0.22~0.25** (3,000 RPS 0.32~0.33) | 2 vCPU 중 대부분이 놀고 있음 |
| Hikari 대기 | 0 | 0 | DB 연결 부족 없음 |

막힌 곳은 Kafka 앞, Redis Queue에서 꺼내는 단계다. 워커 CPU가 남는데도 느린 것은 **순서대로 하는 Redis 왕복, 고정 100ms 대기, 회차당 건수 한도**라는 Bridge 구조 때문이다.

### A는 왜 괜찮은가

A의 서버도 각각 같은 상한을 가진다. 오히려 A 서버의 claim 호출은 **4.3~5.9ms**로 B 워커(1.79ms)보다 느리다. 같은 JVM이 HTTP 요청 1,000건/s를 함께 처리하기 때문이다. 그래서 A 서버 1대의 발행은 1,400~1,800건/s(회차 460~610ms)에 그친다. 하지만 **3대가 동시에** 하므로 합계 약 4,700건/s가 된다(30만 건 A-2 같은 구간). Queue는 최대 1.9만~4.8만에서 멈추고, 매진 1~3초 뒤 DB 반영이 끝난다.

## 원인 2: 3,000 RPS 응답 꼬리가 긴 이유는 느린 서버 1대의 비중이다

### 서버별로 보면 같은 역할끼리는 처리 시간이 거의 같다

안정 구간 280초, 참여 요청(`/api/campaigns/{id}/participation`) 기준이다(A-2·A-3, B-2·B-3).

| 서버 | 받은 요청 | 서버 처리 평균 | 서버 p99 | Redis 명령 평균 |
| --- | ---: | ---: | ---: | ---: |
| A 빠른 서버 ① (2a) | 1,000건/s | 4.2~4.4ms | 36~42ms | 1.5~1.6ms |
| A 빠른 서버 ② (2b) | 1,000건/s | 3.7~3.9ms | 24~31ms | 1.5ms |
| **A 느린 서버 (2b)** | 1,000건/s | **6.6~6.9ms** | **95~114ms** | **2.2~2.4ms** |
| B 빠른 API (2b) | 1,500건/s | 4.5~5.2ms | 40~54ms | 1.6~1.8ms |
| **B 느린 API (2a)** | 1,500건/s | **6.4~7.2ms** | **82~99ms** | **2.2~2.5ms** |

- **요청이 1.5배가 돼도 서버 1대의 처리 시간은 거의 그대로다.** 빠른 서버끼리 약 15% 늘었고, 느린 서버끼리는 같다.
- **A에도 B에도 "느린 서버"가 1대씩 있다.** 느린 서버는 서버 p99가 다른 서버의 2~4배이고, Redis 명령 시간도 더 길다.
- A에서는 느린 서버가 전체 요청의 **1/3**을 받고, B에서는 API가 2대뿐이라 **1/2**을 받는다. 그래서 전체 k6 p95·p99가 나빠진다.

### 확인했지만 원인이 아닌 것

| 후보 | 확인 결과 |
| --- | --- |
| Redis 연결 경합 | B API의 Redis 명령은 3,000건/s로 A의 1.35배지만, 명령 평균 시간은 A와 같다 |
| Tomcat 스레드 부족 | B API 바쁜 스레드 최대 33개 / 200개 (평균 6~15개) |
| DB 연결 부족 | Hikari 대기 0 |
| GC | 분당 횟수 A 25~26회, B API 28~29회. 정지 시간 비율은 0.5~0.6%로 같다 |
| CPU 포화 | 서버 전체 CPU A 49~55%, B API 55~58% (2 vCPU). 포화 아님 |
| AZ(가용 영역) | 시험 슬롯의 Redis primary(172.31.32.183)는 **2c**, 앱 서버는 2a·2b뿐 → 모든 서버가 똑같이 AZ를 건너 접속한다. 느린 서버도 A는 2b, B는 2a라 AZ와 관계없다 |

### 남은 의문: 느린 서버 1대는 왜 생기는가 (미해결)

여러 대 중 1대만 느려지는 현상은 가상 스레드 켬에서도 보였다([타임아웃 원인 조사](2026-11-09-redis-timeout-cause.md), 11-10 계획 문서 2-c). **이번 시험으로 가상 스레드를 꺼도 생긴다는 것을 확인했다.** 느린 서버는 Redis 명령 시간도 더 길지만, 그것이 원인인지 결과인지는 아직 모른다. 서버 JFR 기록(Redis 응답 대기, 스레드 상태)을 비교해야 한다.

## 결론

**공용(A)이 나은 이유**

1. Kafka 전달(Bridge)을 3대가 나눠 하므로 발행 상한이 약 3배다. 30만 건에서 매진 1~3초 뒤 DB 반영이 끝난다.
2. 느린 서버 1대가 전체 요청의 1/3만 받으므로 응답 꼬리에 주는 영향이 작다.

**분리(B)가 뒤처지는 이유**

1. 워커 1대의 Bridge 발행 상한이 약 3,460건/s다(Queue 1만 미만에서는 약 2,630건/s). 이것은 CPU가 아니라 Bridge 구조에서 온다(워커 CPU 0.22~0.33).
2. API가 2대라 느린 서버 1대가 전체 요청의 1/2을 받는다.

**정합성과 안정성은 A·B 모두 문제없다.** 12회 모두 202 = 발행 = DB, 5xx·dropped·reclaim·eviction 0이다.
