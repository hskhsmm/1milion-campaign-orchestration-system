# 200만·250만 건 재검증과 11-16 수치 재분석

2026년 11월 17일 공용 앱 3대에서 200만 건과 250만 건을 다시 실행했다. 두 회차 모두 HTTP 202, 상태 API, MySQL 성공, Bridge 발행 건수가 목표와 일치했다. 중복, reclaim, ACK 거부, 5xx는 0건이었고, 부하 종료 후 3초 안에 Queue·in-flight·Kafka lag가 모두 0이 됐다.

[11월 16일 기록](2026-11-16-250m-integrity-validation.md)의 Prometheus 원본이 모니터링 서버에 남아 있어 함께 다시 조회했다. 그 결과 Queue 크기, 클라이언트 p95, Kafka lag 스파이크, 배출 시간 네 가지의 해석이 달라졌다. 콜드 JVM에서 Bridge가 밀리는 이유는 JFR로 확인했다.

## 11-16 수치의 재해석

### 배출 41초는 확인 간격의 하한

11-16 하네스는 Queue·in-flight·lag가 0인 것을 두 번 연속 확인하고, 그 사이에 20초를 쉰다(`stress-test/harness/remote-run.sh`). 그래서 150만·200만·250만이 모두 정확히 41초로 기록됐다. 5초 간격으로 확인한 11-17 회차의 배출은 3초였다.

### Queue 크기는 JVM 예열 상태가 정한다

11-16 보고서의 "250만에서 Queue 최대가 200만보다 작다"는 부하량이 아니라 실행 순서 때문이다. 11-16에 보고서에 없던 150만 606(env-up 뒤 30만 1회 직후)도 같은 날 실행됐다.

| 회차 (직전 대량 부하) | 시작 후 Bridge Redis 호출 평균, 30초 간격 (ms) | Queue 최대 |
| --- | --- | ---: |
| 11-16 606 150만 (30만 1회 뒤) | 104 → 47 → 18 → 12 → 11 → 6.5 → 3.8 | 307,777 |
| 11-17 612 200만 (콜드) | 49.5 → 36.8 → 14.4 → 7.8 → 5.2 → 4.1 | 223,195 |
| 11-16 608 200만 (150만 직후) | 8.9 → 5.4 → 4.3 | 48,346 |

- 같은 시각 Redis 서버의 `evalsha` 처리 시간은 모든 회차에서 약 30µs로 같았다. 지연은 앱 쪽에서 생겼다. redis-exporter가 노드 하나만 보므로, 캠페인 primary의 값이 아닐 수 있다.
- 11-17에는 콜드(612)와 예열(614)을 같은 환경에서 연달아 실행해 차이를 재현했다.
- 1만 건 예열은 부하가 몇 초뿐이라 JVM 예열 효과가 없다.

- 3,000 VU가 응답을 받자마자 다음 요청을 보내는 닫힌 모델에서는 평균 응답 시간 = VU 수 ÷ 처리율이다. 모든 회차에서 실측과 1~2ms 안에서 일치했다.
- Tomcat 기본 스레드 200개 × 3대 = 약 600개가 동시에 처리하고, 나머지 VU는 실행 대기열에서 기다리는 것으로 보인다. 서버 histogram은 처리 시작부터 재므로 이 대기가 빠진다. 연결 수립(`http_req_blocked`·`connecting` 평균 1ms 이하)은 원인이 아니다.

### Redis 메모리

- 11-16에는 회차 사이에 참여 키를 지우지 않았다. 세 캠페인이 우연히 서로 다른 primary에 배치돼(606 → 2.120, 608 → 33.135, 610 → 27.41) 중단 기준에 걸리지 않았다. 610이 608과 같은 primary(250.6MB 잔류)에 놓였다면 중단 기준을 넘었을 것이다.
- 참여 키당 약 123~128B 기준으로, 250만은 빈 primary에서만 가능하다. 300만(약 380MB)은 빈 primary에서도 중단 기준을 넘는다(선형 외삽).
- 메모리 표본은 10초 간격, 중단 확인은 15초 간격이다. 시험 삼아 기준을 30MB로 낮춘 30만 건 회차에서 실제 최대는 38.5MB로, 기준을 약 8.5MB 넘어서 멈췄다. 342MB 기준이라면 5,500건/s에서 최악 약 17MB를 넘어 약 359MB가 될 수 있다. maxmemory 402.7MB보다는 낮다.
- 이 시험 회차에서 서버 접수 = DB = Bridge 발행은 229,321건이었다. k6가 응답을 받지 못한 접수 997건은 중단 시점에 진행 중이던 요청이다. 11-15 598의 2,931건 차이와 같은 종류다.

## 콜드 JVM에서 Bridge가 밀리는 이유 (JFR)

앱 3대를 JFR(`profile` 설정)과 함께 다시 만들어 콜드 상태로 두고, 1만 건 예열 뒤 30만 건을 3,000 VU로 실행했다. 202 = DB = Bridge 발행 = 300,000으로 정합성은 PASS였다. Queue는 부하 내내 쌓여 최대 195,140건이 됐고(순증가 약 2,300건/s), 부하가 끝난 뒤 15초 동안 17.5만 건이 빠졌다(약 1.16만 건/s).

| 관측 (부하 구간 97초, 앱 1대, 다른 2대도 같은 경향) | 값 |
| --- | --- |
| JVM / 머신 CPU | 평균 85.0% / 86.8%, 10초 구간 최고 99~100% |
| 스레드 종류별 CPU (머신 대비) | Tomcat 45.6%, **C2 JIT 18.6%**, Lettuce I/O 8.1%, Kafka 리스너 각 약 2.6%, Bridge 1.6% |
| JIT 컴파일 | C2 163건, 합계 62.9초. 10초마다 6~9.7초, 부하 끝까지 줄지 않음 |
| Lettuce I/O 스레드 2개의 실행 표본 | 한 스레드가 81~88% (3대: 956/1,081, 824/1,018, 998/1,136) |
| Bridge 대기 위치 | `BridgeQueueService.claimBatch`의 Redis 응답 대기. 10초 구간 평균 54~170ms, 최대 4.6초 |
| GC | 일시정지 합 1.2초(1.2%), G1 동시 마킹 16회 |

해석:

1. **한 캠페인의 Redis 트래픽은 앱마다 Lettuce I/O 스레드 하나를 지난다.** 캠페인 키가 해시태그 `{id}`로 노드 하나에 모이고, Lettuce는 노드 연결을 I/O 스레드 하나에 묶는다. 표본이 한 스레드에 81~88% 몰린 것과 맞는다.
2. **Bridge 처리량은 Redis 왕복 시간에 반비례한다.** Bridge는 스레드 하나가 10건씩 순차로 호출하고, API는 Tomcat 약 200개가 동시에 호출한다.
   - 왕복 4ms(예열)면 Bridge는 앱 1대당 약 2,500건/s로, API 접수(약 1,800건/s)보다 빠르다.
   - 왕복 20~70ms(콜드)면 Bridge는 약 150~500건/s로 떨어져 Queue가 쌓인다.
   - API 요청이 끝나면 왕복이 줄어 빠르게 배출된다.
3. **왕복이 길어지는 원인은 CPU 포화다.** Lettuce I/O 스레드 자체는 CPU를 8%만 썼다. 2 vCPU를 Tomcat, C2 JIT(18.6%), G1 동시 마킹이 나눠 쓰는 동안 I/O 스레드가 CPU를 늦게 받는 것으로 보인다. 콜드 JVM에서는 C2 JIT가 부하 내내 CPU의 약 1/5을 쓴다. 예열 상태의 JFR은 수집하지 않아 C2 몫을 직접 비교하지 못했다.

## 한계

- 각 조건 1회 실행이다. 처리율 3~5% 차이는 반복 없이 비교하지 않았다.
- JFR은 콜드 30만 1회만 녹화했다. 예열 상태 비교와 네이티브 GC 스레드 CPU는 없다.
- Kafka 브로커 요청 지표(JMX)가 없어, lag 스파이크의 coordinator 가설은 확인하지 못했다.
- redis-exporter는 노드 하나만 본다.

## 후속 후보

- 대량 시험 전 예열을 1~2분 지속 부하로 바꾼다. 1만 건 예열은 효과가 없다.
- 지연 목표는 서버 p95 또는 고정 도착률 부하로 판정한다. 닫힌 모델의 k6 p95는 처리율 지표로 읽는다.
- 회차 사이 참여 키 정리 또는 보존 기간 정책을 정한다. 250만에서 중단 기준까지 여유가 약 14MB다.
- 콜드 상태 Bridge 처리량: 호출당 claim 크기, 인스턴스 사양, 배포 직후 예열을 한 변수씩 비교한다.
- lag 스파이크 원인 확인이 필요하면 브로커 JMX(OffsetCommit 요청 지연)를 수집한다.
