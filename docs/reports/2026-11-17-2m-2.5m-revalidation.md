# 200만·250만 건 재검증과 11-16 수치 재분석

2026년 11월 17일과 18일, 공용 앱 3대에서 200만 건과 250만 건을 모두 여섯 번 실행했다. 11-17에는 2회, 11-18에는 콜드·예열 상태에서 각 2회다.

- 6회 모두 HTTP 202, 상태 API, MySQL 성공, Bridge 발행 건수가 목표와 일치했다. 중복, reclaim, ACK 거부, 5xx는 0건이었다. 리밸런스는 로그와 카운터를 확인한 11월 18일 회차에서 관측되지 않았다.
- 250만 건은 앞서 대량 부하를 거친 상태에서 재현했다. Redis primary 메모리는 약 328MB였고, 중단 기준 342MB까지 약 14MB가 남았다. k6 p95는 1초 목표를 넘었다.
- 11월 16일의 배출 확인에는 하네스 대기가 포함됐다. 아래에 원시 표본으로 다시 계산한 상한과 Kafka lag 계측 결과를 기록했다.

첫 검증의 성과와 Grafana 캡처는 [11월 16일 보고서](2026-11-16-250m-integrity-validation.md)에 있다.

## 부하 종료부터 배출까지

배출 시간은 **실제 k6 종료 시각**을 기준으로 잰다. 이 시각은 k6 요약 파일이 생성된 시각이다. 배출이 끝난 시각은 다음 두 근거 중 늦은 쪽이다.
- 1초 간격 Redis 직접 표본(`LLEN`·in-flight)이 0이 된 시각
- kafka-exporter가 실제로 수집한 lag 원시 표본(15초 간격, 10개 파티션 합)이 Queue가 비운 뒤 처음 0이 된 시각

이 값은 실제 배출 완료의 상한이다. lag는 커밋 오프셋 기준이라 DB 반영보다 늦게 0이 된다.

### 콜드와 예열 JFR 비교

같은 부하(1만 예열 뒤 30만 건, 3,000 VU, JFR `profile`, ThreadPark 10ms 이상 기록)를 두 상태에서 녹화했다.
- **콜드**: 11-17 617. 앱을 JFR 옵션과 함께 다시 만든 직후다.
- **예열**: 11-19 01:41. 앱 기동 후 대량 4회를 거친 상태이고, `jcmd JFR.start`로 재시작 없이 녹화했다.

| 항목 (부하 구간, 앱 3대) | 콜드 | 예열 |
| --- | --- | --- |
| 반복률 / k6 p95 | 3,818건/s / 2,352ms | 4,934건/s / 1,158ms |
| Queue 최대 | 195,140 | 33,699 |
| 머신 CPU | 86.8~89.2% | 73.4~76.1% |
| C2 JIT CPU (머신 대비) | 17.3~19.6% | 0~3.2% |
| C2 컴파일 (10ms 이상) | 163~177건, 63~69초 | 8~20건, 3~8초 |
| Tomcat CPU | 45.6~49.2% | 40.4~45.7% |
| Bridge가 claim 응답을 기다린 시간 비율 | 59~77% | 33~59% |
| claim 대기 p50 / p95 | 34~85 / 99~129ms | 18~43 / 61~84ms |

claim 대기는 Bridge 스레드(`scheduling-*`)가 `BridgeQueueService.claimBatch`의 Redis 응답을 기다린 ThreadPark만 센 값이다. 100ms 스케줄 간격의 park는 제외했다.

해석:
1. **한 캠페인의 Redis 트래픽은 앱마다 Lettuce I/O 스레드 하나를 지난다.** 캠페인 키가 해시태그 `{id}`로 노드 하나에 모이고, Lettuce는 노드 연결을 I/O 스레드 하나에 묶는다. 콜드 녹화에서 실행 표본이 한 스레드에 81~88% 몰렸다.
2. **Bridge 처리량은 Redis 왕복 시간에 반비례한다.** Bridge는 스레드 하나가 10건씩 순차로 호출하고, API는 Tomcat 약 200개가 동시에 호출한다.
3. **콜드 회차에서는 C2 CPU 사용과 claim 대기 증가가 함께 나타났다.** C2가 CPU의 약 1/5을 사용했고 claim 대기 p50은 예열 회차의 약 2배였다. 각 상태를 한 번씩 계측했으므로 JIT만의 영향은 분리하지 못했다.
4. **예열 상태에서도 대기는 남는다.** C2 몫이 거의 없어도 API 부하 중 claim 왕복 p50은 18~43ms다. 같은 시각 앱 서버(2 vCPU)의 실행 대기열은 평균 4.8~6.2개(최대 104개)였다. I/O 스레드가 Tomcat과 CPU를 나눠 쓰며 늦게 받는 것과 맞다.
5. 같은 연결에 API 명령이 줄 서는 효과와 CPU 대기 효과는 JFR만으로 나누지 못했다.

2. 다음 poll은 그동안 쌓인 레코드를 한 번에 받는다. 묶음당 약 10건이 약 40건이 된다.
3. 큰 batch INSERT로 처리하므로 처리량은 유지된다. DB 초당 반영이 멈추지 않았다.
4. 커밋은 묶음마다 한 번이라 커밋 횟수가 약 1/4로 준다.
5. 커밋되지 않은 레코드가 lag로 보이다가, 다음 scrape(15초) 안에 0으로 돌아온다.

브로커의 커밋 처리 시간은 평소와 같았다. 11월 18일 계측에서는 커밋 요청이 줄고 Consumer 배치가 커지는 동안 브로커의 커밋 지연은 평소 수준이었다. 11월 16일 스파이크에 같은 메커니즘이 적용됐는지는 확인하지 못했다.

세 대가 동시에 느려진 계기:
- 리스너는 MySQL batch INSERT만 한다(`ParticipationEventConsumer.java`).
- 11-18 r2에서 1초 간격으로 잰 MySQL 조회 왕복은 평소 중앙값 68ms에서 200~600ms로 튀는 순간이 있었다. 아래 매분 :00~:02초 시점과 그 밖의 시점 모두에서 나타났다.
- lag 상위 시점이 이 둘 중 하나와 늘 겹치지는 않아, 계기는 "순간적인 DB 응답 지연"까지만 말한다.
- RDS 1분 지표에서는 스파이크가 있던 분의 RDS CPU가 그 구간 최고(40~42%, 다른 분 31~35%)였다. 쓰기 지연과 디스크 큐는 일정했고, CPU 크레딧 잔고는 0이었다.

매분 초반에 처리량 하락과 호스트 CPU steal이 함께 관측됐다. 발생 원인과 관리형 Redis·RDS와의 인과관계는 미확인이다. [초 단위 관측](#부록-매분-0002초-처리량-하락)을 참고한다.

## Redis 메모리

- 11-16에는 회차 사이에 참여 키를 지우지 않았다. 세 캠페인이 우연히 서로 다른 primary에 배치돼 중단 기준에 걸리지 않았다(606 → 2.120, 608 → 33.135, 610 → 27.41). 610이 608과 같은 primary(250.6MB 잔류)에 놓였다면 중단 기준을 넘었을 것이다.
- 참여 키당 약 123~128B 기준으로, 250만 건은 시작 메모리가 약 8~10MB인 primary에서 검증했다. 기존 키가 더 많이 남아 있으면 중단 기준을 넘을 수 있다. 300만(약 380MB)은 빈 primary에서도 중단 기준을 넘는다(선형 외삽).
- 메모리 표본은 10초 간격, 중단 확인은 15초 간격이다.
  - 기준을 30MB로 낮춘 30만 건 회차에서 실제 최대는 38.5MB로, 기준을 약 8.5MB 넘어서 멈췄다.
  - 342MB 기준이라면 5,500건/s에서 최악 약 17MB를 넘어 약 359MB가 될 수 있다. maxmemory 402.7MB보다는 낮다.
- 이 회차에서 서버 접수 = DB = Bridge 발행은 229,321건이었다. k6가 응답을 받지 못한 접수 997건은 중단 시점에 진행 중이던 요청이다. 11-15 598의 2,931건 차이와 같은 종류다.

## 11월 19일 예열과 250만 건 진입 기준

같은 앱 이미지와 서울 리전 공용 앱 3대 고정 구성에서 실행했다. 30만 건 사전 시험과 250만 건에는 k6 `shared-iterations` 3,000 VU를 사용했다. 지속 예열은 앞서 250만 건 목표 시험을 겪은 앱에서 수행했으므로, 이 결과로 재기동 직후의 예열 효과를 분리할 수 없다.

| 캠페인 | 조건과 결과 |
| --- | --- |
| 628·629 | 재기동 후 각각 2만 건 예열. 두 회차 모두 접수·발행·DB 저장 20,000건 일치 |
| 630 | 250만 건 목표 시험에서 Queue 최대 434,628건, primary 최대 344.4MB. 342MB 가드로 중단했다. 서버 접수·Kafka 발행·DB 저장은 각각 2,429,716건으로 일치했고, 중복·DLQ 0건. 종료 61초 후 Queue·in-flight·lag 0 확인 |
| 631 | 기존 k6 스크립트에 요청률 상한을 적용해 약 300건/초로 36,000건을 120.1초 동안 예열. 정합성 PASS |

630의 대상 primary 메모리는 8.3MB에서 시작했고, 배출 뒤 Queue 0 상태에서 315.9MB였다. 피크 대비 28.5MB가 줄어, 접수 키 누적에 Queue 적체가 메모리 부담을 더한 것으로 보인다.

632의 사전 기준은 본부하 후반 Queue 최종 30,000건 이하, 같은 구간 증가 5,000건 이하, 마지막 Prometheus 표본의 Bridge 발행률/접수율 95% 이상이었다. Queue는 14,916 → 18,030건으로 기준을 충족했다. Prometheus 비율은 15:19:59 KST에 72.5%여서 250만 건을 시작하지 않았다. 이 비율은 전체 API 202와 캠페인별 Bridge 카운터의 1분 범위 `rate()`를 나눈 값이다. 1분 미만의 본부하에서 Bridge 시계열은 부하 시작 약 30초 뒤부터 값이 있어 첫 표본과 조회 창 차이의 영향을 받는다.

반면 15:19:48~15:20:07의 같은 캠페인 Redis 표본에서는 재고가 94,611건 줄고 Queue는 3,114건 늘었다. Queue에서 빠져나간 수를 단순 추정하면 91,497건(96.7%)이다. 이는 in-flight·재처리를 대조하지 않은 추정치로, Kafka 발행 완료 건수는 별도로 확인해야 한다. 두 방식의 결과가 달라 **이번 계측만으로 250만 건 진입 기준을 확정할 수 없다.**

후속 시험은 한 캠페인의 정확한 접수·Kafka 성공 발행 카운터를 부하 전부터 동일한 시간 경계로 표본화하고, 같은 구간 Queue·in-flight와 대조한다. Redis 시작 메모리와 342MB 가드를 유지하고, 사전 기준을 고정한 뒤 250만 건을 실행한다. 실행 ID는 `integrity-20261119T054539-86934`(630), `integrity-20261119T061354-89172`(631), `integrity-20261119T061849-90196`(632)이다.

## 한계

- 대량 회차는 조건별 2~3회다. 처리율 3~5% 차이는 비교하지 않았다.
- JFR은 콜드·예열 각 30만 1회다. 네이티브 GC 스레드 CPU는 없다.
- lag 스파이크의 계기(순간 DB 응답 지연)는 하나로 확정하지 못했다. RDS 내부 지표(초 단위)는 수집하지 않았다.
- 매분 steal의 AWS 쪽 원인은 확인할 수 없다. 비버스트형 인스턴스와의 비교는 하지 않았다.
- redis-exporter는 노드 하나만 본다.
- 11-16 회차는 앱 로그와 reclaim·ACK 거부 카운터가 없다.

## 후속 후보

- 대량 시험 전 예열을 1~2분 지속 부하로 바꾸고, 예열 효과를 같은 조건의 반복 시험으로 확인한다.
- 지연 목표는 고정 도착률 부하로 판정하고, 클라이언트·서버 p95를 함께 기록한다.
- 회차 사이 참여 키 정리 또는 보존 기간 정책을 정한다. 250만에서 중단 기준까지 여유가 약 14MB다.
- Bridge Redis 대기를 줄이는 변경(전용 연결, claim 크기, 인스턴스 사양)은 한 변수씩 비교한다.
- 매분 steal: 같은 부하를 비버스트형 또는 더 큰 인스턴스의 앱으로 1회 실행해 패턴이 사라지는지 본다.
- 앱 `ConsumerFactory`에 Micrometer 리스너를 붙여 Kafka 클라이언트 지표(commit latency, rebalance)를 상시 수집한다.

증상 (11-18 두 회차 이상에서 재현):
- **DB 반영**: 초 단위 반영을 분 안의 초별로 평균하면 :00~:02초가 중앙값의 40~64%다.
