# 가상 스레드 부하에서 Redis 타임아웃·서버 동결 원인 조사 (2026-11-09)

A/B의 A3 회차에서 난 Redis 2초 타임아웃과 "5xx인데 접수" 현상을 AWS에서 재현해 조사했다. 시간순 실행 기록과 원본 증거는 저장소 밖 작업 기록에 보관했다.

**결론 (11-10 갱신):**

1. **콜드 3,000 RPS의 타임아웃·지연 원인은 가상 스레드 스케줄러의 캐리어 수다.** 기본값은 CPU 수(2)다. 캐리어 2개일 때 10회 중 VALID 0, 4개 2/3, 8개·16개 각 3/3이었다. 8개에서 Lettuce 타임아웃 0, 락 대기 최대 43ms, k6 p95 51~68ms로 끔(113~159ms)보다 빨랐다. Tomcat 락 줄서기와 Lettuce 락 대기는 캐리어가 모자랄 때 나타나는 증상이다. Tomcat 캐시 가설은 시험 후 기각했다.
2. **예열 5,000 RPS에서는 캐리어 8개로도 끔에 못 미쳤다.** 2회 모두 INCONCLUSIVE(dropped 1,841·639, 5xx 0, 타임아웃 0)였고, 끔은 3회 모두 VALID였다. 캐리어 2개 때의 FAIL·동결은 사라졌다. 남은 차이의 원인은 미확정이다(아래 "예열").
3. **150만 건은 캐리어 8개와 끔 모두 PASS였고 k6 지연이 비슷했다**(p95 1,060 대 1,141ms). 깨끗한 환경의 끔 150만 Redis primary 최대는 188.6MB로, 중단 기준 192MB에 가깝다.
4. **"동시 처리 상한이 없어서 느리다"는 기각했다.** 켬 + 캐리어 8에 시험용 동시 처리 상한 200을 걸자 3,000 RPS도 미달(p95 1,022ms)이 됐고, 5,000 RPS는 더 나빠졌다(p95 1,572~2,502ms). 같은 200건 동시 처리에서 끔은 5,000 RPS를 소화하므로, **가상 스레드 모드는 요청 1건당 시간이 더 길다.** 그 시간이 어디서 늘어나는지는 미확정이다(pinning 0, 락·GC는 설명할 크기가 아님).

**결정 (11-10):** t3.small(2 vCPU) 공용·분리 구성에서는 **가상 스레드 끔**을 기준 설정으로 쓴다. 콜드 3,000, 예열 5,000, 150만 건을 모두 통과한 유일한 설정이고 힙도 가장 작다. 이후 A/B·장애 시험은 끔으로 한다. 코드·배포 설정 반영은 별도 PR로 한다.

코드 수정은 미커밋이고, 운영 설정(가상 스레드·캐리어 수)은 아직 바꾸지 않았다.

## 시험 조건

- 코드·이미지 `a6f8a02`, digest `32fc3cfc6b03`, 공용 3대(`combined-fixed`, `t3.small` 2 vCPU 1,913MB, 스왑 없음, 컨테이너 한도 1,500MB, `-Xmx1g`). JDK 25, Tomcat 11.0.18, Lettuce 6.8.2, Netty 4.2.10, Lettuce 타임아웃 2초.
- 콜드: 앱 컨테이너 재생성 후 약 1분 안에 부하. 3,000 RPS, 워밍업 30초 + 안정 120초.
- 예열: 1만 건 뒤 3,000 RPS 300초를 먼저 실행.
- 설정 변경은 서버의 compose 파일에만 적용했다(`SPRING_THREADS_VIRTUAL_ENABLED=false`, `-Djdk.virtualThreadScheduler.parallelism=4·8·16`, `maxPoolSize=256`, `SERVER_TOMCAT_PROCESSORCACHE=-1`). 적용 여부는 컨테이너 환경 변수로 매번 확인했다. env-down으로 서버가 내려가 시험 설정은 남아 있지 않다.
- 회차 전체 목록(판정·202·5xx·dropped·k6 값)은 저장소 밖 증거 폴더에 보관했다.

켬 캐리어 2는 `cause-clean` 3회, `cause-jfrlite` 3회, `lockcause` 4회다. 캐시 무제한은 `pcache-r11~13`(`SERVER_TOMCAT_PROCESSORCACHE=-1`), 캐리어 8·16은 `carrier8-r21~23`·`carrier16-r24~26`(`-Djdk.virtualThreadScheduler.parallelism=8`·`16`, `maxPoolSize=256`)이다. 매 회차 앱 컨테이너를 재생성한 콜드 JVM이다. 끔은 JFR을 켠 상태다. 락 대기는 JFR(`JavaMonitorEnter` 5ms 이상) 기록 라운드에서만 쟀다. 회차별 3대 값은 로컬 `cause-20261109/pcache-compare.txt`, `carrier-compare.txt`에 있다.

**판정 (결과를 보기 전에 정한 기준):** 캐리어를 늘릴수록 VALID가 늘고 지연이 끔에 가까워지면 캐리어 부족이 원인, 4에서 멈추면 다른 원인, 나빠지면 다른 가설. 결과는 2→4→8에서 단계적으로 좋아졌고, 8부터 3회 모두 VALID이며 끔보다 p95가 낮았다. 16은 8보다 낫지 않았다. **콜드 3,000 RPS에서 원인은 가상 스레드 스케줄러의 캐리어 수(기본값 = CPU 수 2)다.** Tomcat 캐시 무제한은 `ConnectionHandler` 줄서기만 줄이고 dropped·지연·Lettuce 락 대기는 남아 주 원인이 아니다. 두 락의 줄서기는 캐리어가 모자랄 때 나타나는 증상으로 본다.

### 동시 처리 상한 시험 (11-10, `cl-a-*`·`cl-b-*`)

질문: 예열 5,000에서 켬 + 캐리어 8이 끔보다 못한 것은 동시 처리 상한이 없어서인가. Tomcat 11.0.18의 가상 스레드 실행기에는 상한 설정이 없어(`javap` 확인) 시험 전용 필터(공정 `Semaphore`, 초과 요청은 대기)를 `a6f8a02` 사본에 넣은 jar로 서버 컨테이너의 `/app/app.jar`만 바꿨다. 이미지 digest는 같고 저장소·ECR·운영 배포는 바꾸지 않았다. 새 env-up 환경(서버 3대 교체, Redis 새로 생성)이다.

| 예열, 켬 + 캐리어 8 | A: 상한 없음 (같은 시험 jar) | B: 상한 200 | (참고) 끔 |
| --- | --- | --- | --- |
| 3,000 RPS 300초 | VALID, p50 5 / p95 30 / p99 85ms | **INCONCLUSIVE** (dropped 13,896), p95 1,022 / p99 1,371ms | VALID |
| 5,000 RPS 1회차 | VALID, p95 456 / p99 1,154ms | **INCONCLUSIVE** (45,836), p95 2,502 / p99 3,291ms | VALID, 264 / 406ms |
| 5,000 RPS 2회차 | INCONCLUSIVE (13,720), p95 873 / p99 1,827ms | **INCONCLUSIVE** (22,463), p95 1,572 / p99 2,355ms | VALID, 207 / 334ms |
| 서버 p99 최대 (필터 대기 제외) | 1,354~2,006ms | 435~462ms | 약 160ms |
| CPU 최대 (5,000) | 0.76~0.88 | 0.74~0.80 | 0.79~0.86 |
| 5xx · Lettuce 타임아웃 | 0 · 0 | 0 · 0 | 0 · 0 |

- **사전 기준:** A 미달·B VALID면 상한이 원인, B도 미달이면 원인 아님. A 1회차가 VALID라 대조가 경계였지만(지연은 이전과 같은 양상), B는 3,000부터 미달이라 결론은 같다. → **기각.**
- B의 3,000 회차 서버 p99는 처음 2분 33~57ms였다가 끝에 약 490ms까지 계속 올랐다. 필터 대기를 뺀 처리 시간이 길어졌다는 뜻이다.
- 같은 동시 200건에서 끔은 5,000 RPS를 내려면 요청당 평균 40ms 안에 끝나야 하고 실제로 소화했다. B는 CPU가 남는데(0.74~0.80) 소화하지 못했다. **가상 스레드 모드의 요청당 대기 시간이 더 길다**는 뜻이다.
- JFR 5,000 구간(A 2회, B 1회, 3대): pinning 0, `VirtualThreadSubmitFailed` 0, 5ms 이상 락 대기 최대 35~164ms, GC 멈춤 합계 1.7~2.8초/146초·최대 51~193ms, 컨텍스트 스위치 2.0~2.7만/s. 수 초 지연을 설명할 신호는 없었다. 스케줄러 대기 시간은 JFR 기본 설정으로 잡히지 않고, 끔 회차 JFR과 같은 방식으로 비교하지 않았다. **"왜"는 미확정**이다.
- 필터 방식이 끔(Tomcat 200 스레드, 초과 요청은 서버 밖 연결 대기)과 완전히 같은 조건은 아니다. 요청마다 가상 스레드를 만든 뒤 세마포어에서 기다린다.

## 그라파나 p99 튐

사용자가 공유한 그래프의 p99 1.4초 튐(150만 건, 켬, 21:12:30쯤)은 한 서버의 일시 느려짐이다. 부하 시작 약 240초에 `.101.102`에서 p99 2,064ms, 요청 최대 3,201ms, 힙 776→1,024MB, GC 30초당 1.8초, Bridge 발행 1,345→624건/s가 함께 나타났다. 패널의 1분 rate 평균 때문에 3대 합산 그래프에는 1.4초로 보인다. 끔 150만에서는 이 구간이 없었다. 5xx가 없었던 이유는 VU 3,000 시험이 응답이 느려지면 요청도 줄이기 때문으로 본다 [추정].

## 무슨 일이 일어나나

```text
CPU 포화(콜드 JIT 또는 고부하) + 캐리어 2개
 → 가상 스레드 요청 적체 (느려진 서버 2,000~4,500개, 정상 70~330개)
 → Tomcat 전역 락에 수백~1,491개 BLOCKED
 → Lettuce 이벤트 루프가 selector 락에서 잠듦(최대 3,380ms)
 → 그 루프가 맡은 Redis 연결의 명령이 2초 타임아웃 → 5xx, 일부는 이미 접수
 → 적체가 더 쌓이면 힙 1GB, 호스트 메모리 고갈 → 디스크 스래싱·서버 동결 → 다른 서버로 연쇄
```

각 단계는 측정했지만 단계 사이의 인과는 일부 추정이다. 캐리어를 8개로 늘리면 콜드 3,000에서 사슬 전체가 사라졌으므로, 첫 고리는 CPU 포화 자체보다 캐리어 부족이다(끔도 CPU는 포화였다).

### 스레드 덤프 (`lockcause` 라운드, 느려진 서버와 정상 서버)

| | 느려진 서버 | 정상 서버 |
| --- | ---: | ---: |
| 가상 스레드 | 1,960~4,507개 | 70~330개 |
| `ConnectionHandler` 락 BLOCKED | 243~1,243개 | 0~12개 |
| `RecycledProcessors` 락 BLOCKED | 24~415개 | 0개 |

락 보유자로 찍힌 스레드의 스택은 `ArrayList.remove` ← `RequestGroupInfo.removeRequestProcessor` ← `RequestInfo.setGlobalProcessor`다. 처리 중인 프로세서 수에 비례해 느려지는 작업이 전역 락 안에 있다. 이 함수 샘플은 콜드 JFR에서 느려진 서버의 상위에 있었고 정상 서버 상위에는 없었다.

**Tomcat 캐시 가설(시험 후 기각):** `server.tomcat.processor-cache` 기본값 200을 넘는 동시 처리에서는 요청마다 프로세서 등록·해제가 반복된다는 가설이었다. `SERVER_TOMCAT_PROCESSORCACHE=-1`(무제한) 콜드 3회에서 `ConnectionHandler` 줄서기는 최대 136개로 줄었지만 `RecycledProcessors` 줄서기가 최대 866개였고, dropped 9,815~12,051, Lettuce 락 대기 최대 1,840ms가 남았다. 캐리어를 8개로 늘리자 두 락 줄서기와 지연이 함께 사라졌으므로, 이 락들은 원인이 아니라 캐리어 부족으로 가상 스레드가 쌓일 때 드러나는 증상으로 본다.

### Lettuce 락 (`lockcause-r2`, 타임아웃 508건, `i-0b2e`)

- 19:30:09.349부터 3,380ms 대기. 위치 `EPollSelectorImpl.clearInterrupt`, 직전 소유자 `tomcat-handler`.
- 샘플러: 19:30:10~11에 해당 스레드 CPU 0ms/s, 실행 대기 0ms/s, 상태 `futex`. **CPU 차례를 기다린 것이 아니다.**
- 다른 이벤트 루프는 같은 시각 `ep_poll`로 정상. 이벤트 루프 1개가 멈추면 그쪽 연결만 타임아웃되므로 EVALSHA 위주로 터진 회차와 맞는다(연결 대응은 직접 보지 않음).
- 5ms 이상 대기 기록에 같은 락의 가상 스레드 대기자는 없었다. 덤프에서도 보유자가 비어 있다. 줄서기 가설은 Lettuce 락에 대해서는 증명되지 않았다.
- 덤프는 스레드를 차례로 찍어 한순간이 아니고, 요청이 0.4초 대기 뒤라 찍히기까지 약 1초 걸렸다.
- **해석 [추정, 캐리어 실험과 일치]:** 직전 소유자가 `tomcat-handler` 가상 스레드다. 가상 스레드는 락을 쥔 채 실행 차례를 기다릴 수 있고, 그 차례는 OS가 아니라 JVM 스케줄러의 캐리어(기본 2개)가 준다. 캐리어 2개가 수천 개 가상 스레드를 돌리는 동안 락 보유자가 순서를 기다리면, Lettuce 스레드는 CPU 0·OS 실행 대기 0인 채 `futex`에서 기다린다. 캐리어를 8개로 늘리자 이 대기가 43ms 이하로 줄었다. 보유자가 실제로 캐리어를 기다리던 장면을 직접 찍지는 못했다.

## 5xx인데 접수

`cause-clean-r2` 대조: k6 5xx 사용자 140명 중 **7명이 DB `SUCCESS`**, 호출 위치가 `checkDecrEnqueue`인 타임아웃 7건, DB − 202 = 7건으로 모두 일치. 6건의 순번이 66215~66220으로 연속이고, 재고 감시 보간으로 추정한 실행 시각은 타임아웃 로그 직전이다 [추정, 1초 표본]. 타임아웃은 Redis 실행을 취소하지 못한다.

### 수정 (브랜치 `fix/participation-result-unknown`, 미커밋)

| 상황 | 이전 | 수정 후 | 바로 재시도 |
| --- | --- | --- | --- |
| Lua 타임아웃·연결 실패 | 500, 재시도 429 | **503 `PARTICIPATION_007`** (결과 불명) | 접수됐으면 409, 아니면 202 |
| Rate Limit 타임아웃·연결 실패 | 500, 재시도 429 | **503 `PARTICIPATION_005`** (미접수) | 202 |

둘 다 Rate Limit 키를 해제한다. 해제 실패는 무시한다(TTL 10초). 보상 차감은 하지 않는다. 중복은 Lua의 참여 키가 막는다.

검증: 단위 12건, 전체 142건(실패 0, 건너뜀 24), 실제 Redis와 `CLIENT PAUSE` 재현 3건 통과. 재현에서 재시도 시 재고가 다시 줄지 않았다.

**알아둘 점:**
- 수정은 응답을 정직하게 할 뿐 타임아웃과 "접수됐는데 503"을 없애지 않는다.
- 해제 명령도 타임아웃되면 요청이 최대 약 2초 더 걸릴 수 있다.
- 마지막 재고에서 결과 불명이면 캠페인 DB 종료가 호출되지 않는다. 기존 정합성 복구 Job에 의존하며 이 경로를 시험하지 않았다.
- AWS 부하 검증 전이고 이미지도 배포하지 않았다.

## 미검증

- Lettuce 락 보유자가 실제로 캐리어를 기다렸는지(직접 관측 없음).
- 예열 5,000에서 캐리어 8이 끔에 못 미치는 정확한 이유. 힙·처리 중 요청 증가는 관측, 인과는 추정.
- 캐리어 8에서 150만 건 서버 p99 1.3초 튐의 원인(덤프·JFR 원본은 로컬에 있음, 미분석).
- 캐리어 6·12 등 중간값, 캐리어 8의 장시간·장애 시험, 200만 건. 분리 구성(B)에서의 재현.
- 왜 1대만 먼저 느려지는지(라운드 1개 비교).
- 예열 상태의 산발적 0.5~1.4초 지연의 정확한 원인(끔 일부 회차에도 550ms).
- 수정본의 AWS 부하 동작. `Tomcat 200 스레드` 상한에서 더 높은 부하.

## 남은 위험

- 현재 운영 설정(가상 스레드 켬, 캐리어 2)은 콜드 스타트나 부하 상승 때 타임아웃과 동결이 날 수 있다.
- 캐리어 8로 바꿔도 예열 5,000 RPS에서는 목표 부하 미달이 났다. 끔보다 힙을 2~4배 써서 메모리 여유가 작다.
- 2GB 서버, 스왑 없음, 컨테이너 1,500MB에서 메모리가 차면 OOM으로 재시작되지 않고 수십 분 얼어붙을 수 있다. 헬스 체크 교체가 정지돼 있으면 복구되지 않는다.
- 끔 상태는 스레드 200개에 못 들어간 요청이 서버 지표 밖에서 기다리므로 서버 p99만으로 판단하면 안 된다.
- 150만 건 Redis primary 188.6MB는 중단 기준 192MB에 가깝다. 200만 건은 넘을 가능성이 높다 [추정].
